## Case全体の構成

### system-understanding

旧構成：Context → Problem → Decision → Implementation → Result → What I Would Change Now → Related Design Principles

新構成：使い続けるために、まず現行仕様へ到達できるようにする → 仕様書の整理だけでは、問い合わせに答えられない → 復元した仕様を、人とAIが使える情報へつなぐ → QAは答えを決める仕組みではなく、根拠へ戻る入口にする → 一回の調査を、後続の保守へ使える知識に変えた → この事例から得たこと → 関連する設計原則

### three-ai-maintenance

旧構成：Context → Problem → Decision → Implementation → Result → What I Would Change Now → Related Design Principles

新構成：暗号方式の変更を、保守工程全体の問題として捉える → 製品の順位ではなく、問いに必要な情報から選ぶ → 自動復旧を増やす前に、止める条件と責務を決める → AI間の受け渡しで、前提を確認し直す → 承認した仕様を、小さな変更単位で実装する → コード支援から、一連の保守業務へ適用範囲を広げた → この事例から得たこと → 関連する設計原則

## 判断理由の配置

- 仕様復元：利用を終了できない背景、資料の不足を初章で説明。コード・実動作の照合を第2〜5章、人とAIに適した表現を第6〜8章、評価・改善・更新を第9〜11章、再利用した実例と成果の範囲を第12章へ配置。
- 複数AI保守：異常系の影響を第1章、停止と責務の比較を第2章、コード調査と回答の食い違いを第3章、文書化を第4章、人間レビューを通したAI間の受け渡しと承認を第5章、関数単位の実装・試験を第6章、成果と成立条件を第7章へ配置。
- 独立した判断番号の列挙、固定的なAI担当表の反復、未実施の将来構成を成果と混ぜる説明は削除。
