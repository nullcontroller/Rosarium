# ブックマークと記事IDの保守

> R2はレビュー中で本番未反映。Web Locksによる共通経路を実装したが、現環境の繰返し試験で更新消失が再現し、競合防止の受入条件は未達である。API対応の記載を、保存の整合性を確認済みという意味で扱わない。

## 識別・新規登録の条件

同一性は `collection` と実際の Collection `id` の組である。タイトル、URL、主カテゴリ、Bookの章番号、仮想設計の一覧位置は識別子ではない。既存loaderは変更しない。公開済みIDの保護規約は [Authoring Guide](authoring-guide.md#公開済み記事idの維持) を正本とする。

`src/lib/bookmark-catalog.mjs` の同一判定を記事ボタンと公開カタログの双方で利用する。新規登録は pages、公表可、published/stable、active、互換URLへ転送されない独立した本文ページに限る。件数は固定しない。Career、一覧用原稿、非公開・旧・退役記事には登録ボタンを出さない。

## 保存形式

専用キーは `rosarium.bookmarks`。他のキーには書き込まない。

```json
{
  "schemaVersion": 1,
  "site": "rosarium",
  "items": [
    {
      "collection": "pages",
      "id": "foundations/conditional-probability",
      "addedAt": "2026-11-27T00:00:00.000Z",
      "titleSnapshot": "自己回帰型生成AIの条件付き確率モデル",
      "urlSnapshot": "https://rosarium-tech.com/foundations/conditional-probability/"
    }
  ]
}
```

タイトルとURLのスナップショットは任意であり、同一性に利用しない。未解決時のタイトル表示にだけスナップショットを利用し、スナップショットURLをリンクへ採用しない。登録元IDは統合後も書き換えない。

内部データの破損・異常値を検出するため、UTF-8で1MiB、2000項目、ID256文字、collection32文字、タイトル400文字、URL2048文字を上限とする。日時は有効なUTCのISO表記（秒またはミリ秒3桁）とする。不明なキー、未知のschema/site、不正型・日時・IDを拒否する。URLスナップショットは認証情報を含まない正規本番ホストまたは旧GitHub Pages配下のHTTPSだけを許可する。外部URL、javascript等を拒否する。保存済み文字列はtextContentだけで表示する。

## 公開カタログ

`/bookmarks.json` は Content Collection からビルド時生成する静的JSONである。専用の閲覧HTMLページは追加しない。検索インデックスは利用しない。最小限の解決情報はcollection/id、最新タイトル、閲覧URL、主カテゴリ、ライフサイクル、新規登録可否、解決状態、明示的な後継記事である。本文や非公開原稿は含めない。

既存の互換URL登録正本でdispositionが「簡素化」となっている記事の転送だけを後継関係として解決する。統合・廃止された一覧からカテゴリやBookへの案内転送を、記事の後継関係とみなさない。直接閲覧できる旧・退役記事は状態付きで表示する。後継記事が解決できないIDは「現在利用できない」とし、データを保持する。類似タイトルから推測しない。既存の404は修正しない。

## 操作・失敗・競合

記事見出しの同じボタンで登録・解除する。書込み成功後だけ表示を更新する。ヘッダーからnative dialogを開き、カテゴリ別の最新タイトル・リンク・状態・解除を提供する。Escape、Tab循環、閉鎖後のフォーカス復帰に対応する。320pxでは既存ヘッダーを圧迫しないようメニュー内から開く。390px以上のスマートフォンとPCではヘッダーアイコンから開く。

JSONファイルの書出し・読込み・プレビュー・マージは提供しない。既存JSONスキーマと保存済みの項目・スナップショットはそのまま読み取る。解除対象以外の未解決項目も保持する。

すべてのUI書込みは `writeBookmarks` を通る。セキュアコンテキストでWeb Locks APIが利用できる場合、同一origin内の共通名 `rosarium.bookmarks.write` をexclusiveモードで取得し、そのコールバック内でlocalStorageを読み、操作を決定・適用して保存する。記事ボタンの登録／解除判断もロック内の最新状態で決める。パネルの解除は明示的なremove操作であり、既に未登録ならその状態を維持する。保存成功後だけUIを更新する。storageイベントで他タブの表示を更新する。

同一IDへの明示的なaddは重複登録しない。同一IDの明示的なremoveは未登録を維持する。同じ記事ボタンを2タブから同時に押した場合は、ロック内で順次判定する2回のtoggleとして扱う。未登録からなら、登録後に解除され最終状態は未登録となる。明示的なaddとremoveが同じIDに競合する場合はロック処理順の最後の操作が有効となる。異なるIDへの操作は両方を維持する。

APIが存在するのにロック取得が失敗した場合は、保存を行わずエラーにする。排他を外して再試行しない。保存拒否・quota等の保存失敗でも再試行・自動クリアしない。ロックは同期のread-modify-writeを保護し、ネットワーク待機・ダイアログ操作を含めない。試したタスク境界による待機では繰返し試験の不一致を解消できなかったため、タイマー待機を解決策として残していない。

利用拒否、容量超過、破損データではエラーを表示し、既存バイト列の上書きやクリア、成功表示を行わない。storage.clear()は使用しない。破損データの自動修復・破棄は行わない。

localStorageは端末・ブラウザープロファイル・originごとであり、自動同期はない。通常閲覧とステージングの保存領域も別である。Web Locksを使う同一origin・同一ストレージ領域の本実装同士のコールバックを直列化する。ただし現環境ではlocalStorageの読取値を含む更新の整合性検証が未達である。別のキーへの操作、ブラウザーのデータ削除、手動でlocalStorageへ直接書くコードまでトランザクション化するものではない。旧版を開いたままのタブはロックへ参加しないため、更新後は全タブの再読込みが必要である。

Web Locks非対応または非セキュア環境では、既存の同期処理（書込み直前の再読込み）へフォールバックする。この場合、同時書込みの更新消失を防止できるとは保証しない。保存説明はUI簡素化指示に従い「ブックマークはこのブラウザーに保存されます。」に限定し、制約は本運用資料とレビュー資料に明記する。ページを開いたまま公開カタログが更新された場合は、再読込み後に最新情報へ更新される。

## 対応環境の根拠

[W3C Web Locks仕様](https://www.w3.org/TR/web-locks/)はSecureContextでのAPIと同一ストレージ領域の協調的な排他を定義する。[MDNの互換性データ](https://github.com/mdn/browser-compat-data/blob/main/api/LockManager.json)ではChrome 69以降、Firefox 96以降、Safari 15.4以降でrequestが対応し、Chromium Edge・Android／iOS版の対応は各ブラウザーの派生情報として管理されている。これは互換性資料上の対応であり、この作業で全ブラウザーを実機検証したという意味ではない。実行時はUA文字列やバージョン番号ではなくisSecureContextとnavigator.locks.requestの有無を判定する。HTTPSのTailscaleステージングと本番正規ホストはセキュアコンテキストである。実測したブラウザーとバージョンは検証ログに記録する。

保存データを外部へ送信しない。カタログ取得は固定URLのGETだけで、保存IDをクエリやリクエスト本文へ送らない。GA4実装・計測除外設定は変更しない。

## 自動検証

- `npm test`: 保存・スキーマ・状態解決・排他内の再読込とフォールバック・ID不変規約のユニットテスト。
- `npm run check` / `npm run build`: Git全履歴を使うIDガード。導入基準6601fae以後の公開IDを保護し、過去に削除したIDを履歴全体から予約する。
- `node scripts/verify-bookmarks-build.mjs [dist|dist-review]`: カタログとCollectionsの一致、全対象ボタン、非公開情報の不在、登録対象外ページの境界を検証。

Git履歴がない場合は失敗させ、黙って検査を省略しない。新規記事の作成前に履歴中のID再利用にも注意する。意味上の別記事への内容すり替えは自動判定できず、レビューを併用する。
