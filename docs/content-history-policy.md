# 更新履歴の役割

- Garden Notesは日別の更新件数を示す全体ログ。詳細ページは月別に全期間を保持する。
- Homeは日本時間の閲覧日を含む過去30日（当日から29日前まで）。月だけ分かる記録に仮の日付を割り当てない。
- 静的生成時に期間を判定し、ブラウザでも閲覧時・ページ再表示時に判定する。JavaScript無効時は最後のビルド日時点の表示となる。
- 記事・Case・Bookの変更内容は共有 `ContentHistory.astro` で最終更新表示の近くに枠付きボックスで表示する。Careerも同じ表示を使用する。Reference専用ページには追加しない。
- `src/data/recent-growth.ts` の対象ID・action・説明を中央管理し、件数と記事別履歴の双方へ使用する。typo、CSS、微小リンク修正、SEO、開発作業は追加しない。
- `src/data/content-history.ts` が公開イベントを先頭に置き、確認できた実質改訂だけを日付順に返す。表示は新しい順。
- 履歴の説明は、その改訂で読者が新しく読める内容を2〜3文以内で記す。未評価事項、比較データの不足、内部検証・編集・開発事情は載せず、必要な根拠や制約は本文で扱う。
- `update_note` と中央の同日記録が同じ変更を説明する場合は文言を揃え、履歴に同じ内容を重ねない。

## 復元根拠と制限

公開日は `published_at`、`source.published_at`、`source.publication_month`、明示的な新規公開記録を使用する。月しか判明していない場合は月表示を維持する。

今回、公開コンテンツ98件のmetadata、移行manifest、Gitの追加履歴、Garden Notesを確認した。新規Caseと考察の追加は2026-10-07のGit履歴と公開記録が一致する。10月6日の7件は改訂。10月8日はコード生成境界の改訂を統合へ更新し、コード生成と業務設計の記事の統合と開発工程ガイドの改訂を加え、記事16件改訂・記事2件統合・実践事例1件改訂として保持する。

公開日は、確認済みの `published_at`、sourceの公開日・公開月、明示的な公開記録の順で優先する。月しか確認できない場合は月を保持し、日・時刻を創作しない。公開日を確認できない既存の公開コンテンツ（Careerを含む）には、運用上のfallbackとして `published_at: "2026-09-23"` と `publication_date_basis: fallback` を設定する。これは実際の歴史的公開日を主張するものではなく、確認済みの根拠が後から得られた場合はそちらを優先する。Gitの追加日や最終更新日を公開日の根拠にはしない。source metadata、本文、最終更新日、改訂履歴は保持する。

10月5日以前の記録は個別記事IDと正確な更新数を復元できないため、旧記録の詳細データを削除せず、件数を作らない短い全体説明を表示する。今後は対象IDとactionを登録し、集計可能にする。

本文、URL、Lifecycle、SEOの日付はこの表示変更によって変更しない。更新履歴はTOCおよびPagefind本文から除外する。

`update_note` は対応する改訂日に取り込み、同日イベントを増やさず説明を保持する。上部の「今回の更新」は表示しない。履歴は新しい3件を表示し、4件以上は以前の履歴を標準detailsで折りたたむ。
