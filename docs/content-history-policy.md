# 更新履歴の役割

- 庭の「最終更新」は、Rosarium全体で最後に公開変更が入った日。正本は `src/lib/site.ts` の `staticPageLastUpdated[""]` とし、公開コンテンツの追加・改訂・統合・削除、Careerなどの表現整理、ナビゲーションや読者に見えるUIの変更時に更新する。Garden Notesの最新日や個別記事の日付からは導出せず、同じ日付を他の場所へ重複保存しない。公開物に変更のないビルド・デプロイだけでは更新しない。
- Garden Notesは全変更ログではなく、読者へ知らせる価値のある公開・改訂履歴。新規記事・Book・Caseの公開、内容を実質的に変えた大きな改訂、知識や記事の統合・廃止・退役、サイトの主題や代表実績に関する重要な変更、読者が新しく理解・参照できる内容を記録する。既存経験の表現整理を、新しい実績の発生として記録しない。詳細ページは月別に全期間を保持する。
- 個別記事の更新履歴は、その記事自身の公開・実質改訂を扱う。庭の最終更新、Garden Notes、個別履歴は役割が異なり、庭の日付変更だけを理由にGarden Notesや個別履歴を追加しない。
- Homeは日付降順の最新3件を表示する。月だけ分かる記録に仮の日付を割り当てない。全期間はGarden Notesの月別履歴に保持する。
- Garden Notes以外の全ページでは改訂履歴・改訂説明を表示せず、最終更新日だけを重複なく表示する。記事・Book・章・Case・Careerに例外を設けない。Homeの「最近の手入れ」はGarden Notesへの入口として維持する。公開日は通常画面に出さず、metadata・SEO・構造化データ・検索用情報には保持する。共有 `ContentHistory.astro` は最終更新日の表示だけを担う。
- `src/data/recent-growth.ts` の対象ID・action・説明を中央管理し、件数と記事別履歴の双方へ使用する。typo、CSS、微小リンク修正、SEO、開発作業は追加しない。
- `src/data/content-history.ts` が公開イベントを先頭に置き、確認できた実質改訂だけを日付順に返す。履歴データは表示方針にかかわらず保持する。
- 履歴の説明は、その改訂で読者が新しく読める内容を2〜3文以内で記す。未評価事項、比較データの不足、内部検証・編集・開発事情は載せず、必要な根拠や制約は本文で扱う。重要な訂正は例外として、誤った加筆と撤去・訂正した事実、理由を簡潔に残す。
- `update_note` と中央の同日記録が同じ変更を説明する場合は文言を揃え、履歴に同じ内容を重ねない。

## 継続運用の判断基準

記事やサイトの変更を終えるとき、Codexを含む編集者は「今回の変更は、読者に知らせる価値のある実質的な更新か？」を判断する。該当する場合だけGarden Notesを更新し、該当しなければ変更しない。公開内容・実績・成果を推測で補完しない。

誤字・表記揺れ、CSS・装飾、軽微なリンクやナビゲーション、テスト、内部リファクタリング、細かなSEOメタデータ、ビルド・デプロイ、公開内容に変化のない作業は原則記録しない。必要なら個別記事の履歴やサイト全体の最終更新日を、それぞれの役割に沿って更新する。小さな修正だけの日や実際に変更がない日に、Garden Notesを作らない。

日付・見出し・概要は次の基準で整える。

- 原則1日1エントリ。同日の既存記録へ統合し、同じ趣旨の改訂をまとめる。
- 見出しはその日の主要な変更を具体的に表し、現在の公開内容と一致させる。撤去済みの内容を現在の成果として掲げない。
- `summaryChanges` はHomeでも使う短い概要として原則2〜3項目を目安とする。1日の作業を時系列で細かく並べず、詳細は `changes` と記事別履歴へ委ねる。
- 訂正があっても過去の追加を隠さず、主な改訂を先に、必要な訂正は短く添える。通常の整理では過去の日付・履歴を不必要に書き換えない。
- 公開日は最初の公開、改訂日は内容を変更した日、履歴記録日はその変更を記録する日であり、混同しない。後から記録する場合も根拠のある変更日を使い、今日の日付を公開日や改訂日へ機械的に代入しない。
- `contentIds` と `action` を維持し、重複日付・重複ID・存在しない対象を検証する。ACTIVE / OBSOLETE / RETIREDの位置付けを変えず、同じ改訂の説明は重複表示しない。

判断後は、Homeの最近の更新、Garden Notesの月別表示、対象記事の履歴が同じ変更を矛盾なく伝えているか確認する。Garden NotesはGitのコミットログや開発日報にしない。

## 復元根拠と制限

公開日は `published_at`、`source.published_at`、`source.publication_month`、明示的な新規公開記録を使用する。月しか判明していない場合は月表示を維持する。

今回、公開コンテンツ98件のmetadata、移行manifest、Gitの追加履歴、Garden Notesを確認した。新規Caseと考察の追加は2026-10-07のGit履歴と公開記録が一致する。10月6日の7件は改訂。10月8日はコード生成境界の改訂を統合へ更新し、コード生成と業務設計の記事の統合と開発工程ガイドの改訂を加え、記事16件改訂・記事2件統合・実践事例1件改訂として保持する。

公開日は、確認済みの `published_at`、sourceの公開日・公開月、明示的な公開記録の順で優先する。月しか確認できない場合は月を保持し、日・時刻を創作しない。公開日を確認できない既存の公開コンテンツ（Careerを含む）には、運用上のfallbackとして `published_at: "2026-09-23"` と `publication_date_basis: fallback` を設定する。これは実際の歴史的公開日を主張するものではなく、確認済みの根拠が後から得られた場合はそちらを優先する。Gitの追加日や最終更新日を公開日の根拠にはしない。source metadata、本文、最終更新日、改訂履歴は保持する。

10月5日以前の記録は個別記事IDと正確な更新数を復元できないため、旧記録の詳細データを削除せず、件数を作らない短い全体説明を表示する。今後は対象IDとactionを登録し、集計可能にする。

本文、URL、Lifecycle、SEOの日付はこの表示変更によって変更しない。個別ページに履歴枠は描画しない。Garden Notesの月別・日別履歴と過去の記録は保持する。

`update_note` は対応する改訂日に取り込み、同日イベントを増やさず説明を保持する。個別ページには最新1件を含め改訂説明を表示しない。この表示整理だけでは記事の日付を書き換えず、Garden Notesの記録も新設しない。
