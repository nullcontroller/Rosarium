# Authoring Guide

このRepositoryはKnowledge / Publishing as Codeの母艦です。本文の正本は標準Markdownです。
既存Zennの文章を統合・要約・リライトする場合は、移行作業と分離してレビューしてください。

## 新規ページ

`src/content/{section}/{semantic-slug}.md`を追加します。通常ページはMDXを使いません。
英小文字・数字・ハイフンのsemantic slugを使い、公開後はURLを安易に変更しません。
ファイルの相対パスがURLになります。例：`foundations/acceptance-boundary.md` → `/foundations/acceptance-boundary/`。

```yaml
---
title: "採否判断の境界"
summary: "このページが扱う範囲を簡潔に記述する。"
kind: principle
section: foundations
layer: ai-design
design_topic: applicability
status: draft
order: 10
tags:
  - Applied AI
  - HITL
published_at: "2026-09-21"
last_updated: "2026-09-21"
update_type: expanded
update_note: "責任境界と実行権限の整理を追加"
---
```

タイトルは共通レイアウトがH1として表示します。本文の見出しは`##`から始めます。
新規記事に出典や日付を捏造しません。公開日・更新日は不明なら省略できます。

`summary`は必須です。本文で実際に扱う内容を1〜2文で要約し、タイトルから推測しません。すべての一覧・章目次・前後リンク・検索結果はこの値だけを概要として表示します。本文を変更したら概要も確認してください。

## 公開済み記事IDの維持

- 公開済み記事IDは原則変更せず、廃止済みIDを別記事へ再利用しない。過去に削除した原稿のIDも再利用防止の対象とする。
- 改題や主カテゴリ変更だけを理由にファイルを改名しない。ファイル移動が必要なら、Collectionの実ID、URL、履歴・Book・関連記事・互換登録などへの影響を事前に確認する。
- Book目次、各章、連載目次・各回は独立したコンテンツとして識別する。seriesや章番号を記事IDの代わりにしない。
- 仮想設計のidBaseと一覧のlistingTargetを分離し、表示位置を変更しても既存IDを生成し直さない。
- 識別はcollectionとidの組で行う。Careerの実IDoverview、履歴表記career/overview、公開URL/career/は異なる役割である。
- `npm run check`と`npm run build`のIDガードは、Git履歴から公開済みIDと削除済みIDを取得し、重複・命名・変更／削除・削除後の再追加を検出する。CIは規約導入基準6601faeを含む履歴を取得する。履歴のない配布ソースで検査を黙って省略しない。
- ルールは削除後の再追加等を自動検出するもので、同じファイルの内容を別記事へすり替える意味上の再利用まで自動判定できるものではない。正当な例外は著者の個別承認とID・URL互換のレビューを要する。ガードを無効化して通さない。

## 記事の最終更新日管理

記事を新規作成・改訂する際は、本文だけでなくFront Matterの更新日を必ず確認します。本節と次節を、記事編集時の更新日・履歴管理の正本とします。

- 本文・概要・設計内容・図解を実質的に変更した場合は、`last_updated`を実際の改訂日に更新します。
- 初回公開日を示す`published_at`は、改訂によって変更しません。
- 誤字修正、タグの表記統一、共通CSS・UIなど、記事の内容に影響しない修正では、原則として更新日を変更しません。
- Bookは変更した章ごとに更新日を確認します。Book概要も変更した場合は別途確認し、未変更の章・記事まで一括更新しません。
- ファイルの変更日時やGitの最終コミット日時を、記事の更新日として自動採用しません。確認できない日付は捏造しません。

最終更新日の正本は`last_updated`です。記事ヘッダー・カード・Book目次・前後ナビゲーション・検索・構造化データ・サイトマップへ同じ値を渡します。既存の`updated_at`は互換用であり、新たな最終更新日の管理先にしません。必要な場合だけ`update_type`（new / updated / expanded / revised / connected / reframed）と1行の`update_note`を追加します。

Markdownを持たない入口・案内ページの日付は、既存の`src/lib/site.ts`の`staticPageLastUpdated`を一つの正本として使います。同じ日付をAstroの`lastUpdated`属性へ重複保存しません。記事由来のページはFront Matterを参照します。一覧の共通カードやパンくずだけの変更を、全記事の本文改訂として扱いません。

一覧に新しい記事や改訂後の概要・更新日を反映した場合は、一覧自身の日付も確認します。生成HTMLの検証は、表示している記事カードより一覧の日付が古い状態を検出します。日付の根拠は掲載記事の`last_updated`・公開日と編集記録とし、ファイルやコミットの日時から作りません。個別記事の本文・公開日を一覧の都合で変更しません。

`npm run check`はGitのHEADと作業中のMarkdownの本文・タイトル・概要を比較し、前日以前の更新日を据え置いた変更を要確認候補として通知します。同日内の追記やタグだけの変更は許容します。文字差分だけでは実質的な改訂と誤字・互換アンカー修正を区別できないため、日付を自動更新しません。変更範囲を確認したうえで`ROSARIUM_REVISION_STRICT=1`を指定すれば候補が残る検証を不合格にできます。過去の改訂を確認する場合は`ROSARIUM_REVISION_BASE`へ比較元、`ROSARIUM_REVISION_DATE`へ根拠を確認した編集日を明示できます。Gitは差分の取得だけに使い、コミット日時から記事の日付を決めません。静的ページの説明や共用図解の影響範囲は引き続き人が判断します。CI等で作業ツリーが既にコミット済みの場合は、比較元を明示して実行しない限り未コミット差分はありません。

`npm run build`では生成HTML、カード、Pagefindの実フラグメント、構造化データ、sitemap、RSS・JSON Feedの日付を照合します。レビュー用も`node scripts/verify-last-updated.mjs dist-review`で選択された未公開記事と一覧を含めて確認します。RSS・JSON Feedの改訂日と並び順も`last_updated`を参照し、`published_at`を改訂日に置き換えません。

## GARDEN NOTESと個別記事の更新履歴

記事の新規公開、実質的な改訂、統合、退役、サイトの重要な機能改善を行った場合は、`src/data/recent-growth.ts`の更新要否を必ず確認します。読者にとって意味のある変更だけを記録し、実際の変更内容と一致させます。

- 記事の変更は、既存の`contentIds`と、内容に対応する`action`（published / revised / integrated / retired）を使い、記事ごとの更新履歴データにも反映します。改訂を新規公開として登録しません。
- サイト共通のUI改善は文字列で管理し、個別記事の改訂履歴へ一律に結び付けません。軽微な装飾・内部保守だけで記録を増やしません。
- 同日の変更は既存の更新記録へ追記・統合します。
- 未公開記事は更新日を管理しても、公開用GARDEN NOTESへタイトル・リンク・IDを登録しません。
- 記録した対象・説明・日付を実際の変更と照合します。記録日が対象記事の`last_updated`より後になっていないことを`npm run check`で検証します。

履歴の公開表示・集計・過去データの保持は[更新履歴の方針](content-history-policy.md)に従います。個別記事の履歴データへ反映することと、記事ページへ履歴ボックスを表示することは別です。

## Layer / Topic / Source

layerは知識の役割、sectionは既存のテーマとURL用分類、source.typeは出典です。これらを混同しません。

| layer          | 役割                                   |
| -------------- | -------------------------------------- |
| ai-design      | 現在の設計知識の正本                   |
| ai-mathematics | 確率・条件付き確率・分布などの数学的基礎 |
| ai-theory | 生成AI・LLMの生成原理、誤答の要因、モデルと周辺システムの仕組み |
| practice       | 組織・業務・開発への適用               |
| case           | 事例（実務か仮想設計かは既存の明示定義で区別） |
| publication    | 独立した記事・Book・Essay              |
| project        | プロジェクトの記録                     |
| reference      | 用語・参照資料                         |

AI Designはdesign_topicも必須です。applicability / responsibility-control / architecture / knowledge-context / evaluation-hitl / software-engineering / lifecycle-operationsから選びます。
既存URLはlayerに合わせて移動しません。旧foundationsの文書も同じURLを維持します。新規本文の物理配置と公開URLは編集時に決め、公開後は維持します。

記事一覧は出版物の横断ビューです。Zenn由来のLLM確率モデル記事のように、layerがai-mathematicsでも出版元情報を保持したまま掲載できます。出典だけでlayerを自動判定しません。
PublicationのTypeはBook、kindがessayならEssay、それ以外はArticle。sourceの元typeは保持し、章はBookの目次から辿ります。未確認の公開日は捏造せず、判明している月だけを「YYYY年M月」と表示します。現在も連載中のBookは`publication_status: ongoing`で「連載中」と表示し、Rosariumでの最終更新日は`last_updated`として別に扱います。

AI Designの正本一覧にはZennを混在させません。Related Publicationsはsrc/lib/navigation.tsの明示的な文書ID対応表で管理します。Case Studiesも同ファイルでBook・注目章・関連原則を接続し、本文は複製しません。

## Section / kind / status

| section              | 内容                                      |
| -------------------- | ----------------------------------------- |
| foundations          | 変わりにくい設計原則                      |
| architecture         | 全体構成・権限・Workflow・Lifecycle       |
| knowledge-context    | RAG・Context・Evidence・情報更新          |
| evaluation-hitl      | 評価・レビュー・承認・判断条件            |
| software-engineering | AIを用いたソフトウェア開発・Orchestration |
| practices            | 教育・導入・横展開・適用判断              |
| cases                | 原則を適用した事例（実務事例・仮想設計） |
| essays               | 市場・キャリア・技術に関する論考          |

`kind`: `principle`, `architecture`, `guide`, `case`, `essay`。
`status`: `draft`（非公開）、`published`（公開）、`stable`（安定）、`archived`（過去資料）。記事の更新状態には使用せず、内容を変更した日は`last_updated`を更新します。
移行時は著者による安定性を推測せず、公開済みContentを`published`として扱います。
Draftはページ生成・ナビゲーション・検索対象から除外しますが、公開GitHubリポジトリのソース自体は閲覧可能です。
機密情報の保存場所として使わないでください。

## 意味構造のDirective

通常の文章・リスト・表・コード・画像は標準Markdownで書きます。
意味を明示する必要がある箇所だけ、以下の7種類を使います。
HTML代わりの独自言語として増やしません。未定義のcontainer directiveはビルドエラーです。

```markdown
:::principle{title="設計原則"}
AIが生成できることと、業務で採用してよいことは別である。
:::

:::decision{title="設計判断"}
AI出力は中間成果物として扱う。
:::

:::risk{title="リスク"}
誤生成だけでなく誤実行まで考慮する。
:::

:::responsibility{title="責任境界"}

- AI：候補生成
- 人間：採否判断
- 既存システム：確定処理
  :::

:::evidence{title="根拠"}
判断に使用した情報や評価結果。
:::

:::case{title="実務事例"}
実際に適用した事例。
:::

:::note{title="補足"}
補足情報。
:::
```

Directiveは段落間の独立ブロックとして使います。`title`は省略できます。
`remark-directive`がASTを解析し、対応するAstro Componentで`section`、`figure`、`aside`として出力します。
通常のコロン記号は独自インライン記法として扱いません。

## 事実性と公開範囲

実務事例は本人の経験と確認済みの事実を基準にし、技術判断の根拠と確認範囲を示します。未実施の作業、未測定の成果、推測した障害原因を実績として補いません。機密情報を公開できない場合も、架空のコード・事例・判断過程で穴埋めしません。具体性が足りなくても、情報不足は確認範囲の限界として扱います。

一般的な技術原則・理論・数式は実務経験と区別します。既存の説明用仮定は必要性と実績との混同を個別に確認し、一括削除しません。AIが作った説明のもっともらしさより事実性と検証可能性を優先します。誤った加筆を撤去する場合は、追加した事実と訂正理由を既存の履歴へ残します。

## 図 / コード / 数式

### AI・数理記事の説明設計と用語

AI・数理の目的は、数学によってAIの仕組みを理解することである。冒頭はAIの具体的な問題から始め、その原因、学習・生成・推論の処理、説明に必要な数学へ進む。数学から始めて末尾だけにAIへの応用を付けない。読者が「AIのどこを扱い、何が問題で、なぜこの数学が必要で、何が分かるか」を自然な導入から理解できる構成にする。

具体例の後に定義と導出を置く。重要な式の直前に求める量を説明し、直近で記号・添字・演算子とAI処理の対応を示す。計算例は、トークンの候補、回答の採点、生成・学習費用などへ対応付ける。人工例を実モデルの性能や特定商用AIの内部実装として扱わない。図は対応する説明の近くへ置き、一図へ詰め込みすぎない。

主要概念は初出で日本語名・英語名・略称、直感、定義、AIでの役割を説明する。前提概念は短く再掲して既存記事へ、補助用語は短い補足又は既存の[基本用語集](/reference/glossary/#ai-math-terms)へ接続する。用語集は `src/content/reference/glossary.md` に集約し、安定したASCIIアンカーを使う。英語の訳だけを定義とせず、未説明語で別の未説明語を定義しない。全用語へカード・ホバー説明・リンクを機械的に付けない。本文だけでも主筋を追えるようにする。

報酬と収益、報酬と損失、方策とモデル、確率とlogit、学習と推論、InferenceとReasoning、FLOPsとFLOPSなど、混同する量を区別する。用語の文脈による定義差を隠さない。分かりやすさを理由に定義、途中導出、支持集合・独立性等の条件、限界、一次資料、Python検算を削らない。公開済み原稿の改訂案は独立ブランチとステージングでレビューし、公開状態を維持したまま本番反映を待つ。

静的な構造図はSVGアセット、操作可能な理解支援図は既存のSVG＋TypeScriptコンポーネントを利用します。
静的図はLight / Darkの既存表示を保存し、JavaScriptに依存せず表示します。コードはShikiでハイライトします。
数式は`$...$`と`$$...$$`に対応し、KaTeXのフォント・CSSもbundleします。
通常の文章ではHTMLの`br`、Markdownの行末2空白・バックスラッシュによる強制改行を使いません。段落を意味単位で分け、画面幅に応じた自然な折り返しを使います。引用、表、コード、数式、図解、連載目次のタイトルと副題など、意味上必要な整形は保持します。スクリプトやiframeをMarkdownへ追加しないでください。

## 画像・リンク

新規画像は`public/assets/`へ配置し、本文では`![説明](/assets/example.png)`と記述します。
共通Markdown処理がサイトのbaseを付加します。現在のbaseは空文字列で、正規ドメイン直下のURLです。Zenn移行画像は`public/assets/imported/zenn/`です。
外部画像の代替を勝手に生成しません。

内部リンクは`[表示名](/foundations/acceptance-boundary/)`のようにカテゴリから始まる絶対パスにします。
末尾スラッシュを付け、`.md`へのリンクにしません。baseはHTML変換時に付加されます。
同ページ内は`#見出し-id`。`npm run build`は内部リンク・画像・アンカーを検査します。

## Series / Book

シリーズ概要：`src/content/cases/example-series.md`。
章：`src/content/cases/example-series/chapter-topic.md`。
全ページに`series: example-series`、`series_title: "シリーズ名"`を設定します。
概要は`order: 0`、章は`order: 1`から連番にします。概要には必要なら`cover: /assets/cover.jpg`。
各章で全章目次・現在の章・前後リンクを自動生成します。
移行Bookの順序は元`config.yaml`の`chapters`を正とします。初回移行では変更しません。

## 出典とcanonical

Zenn由来ページは`source`に元slug、Book/Chapter slug、type、topics、公開日、URL、元front matterを保持しています。
正規ドメインは `https://rosarium-tech.com` です。公開HTMLの正本は `src/layouts/Site.astro` のcanonical生成処理です。

- 通常ページは自ドメインと現在のルートをcanonicalとします。自ドメイン内の明示的なcanonicalは、互換URLから統合先への案内などに使用します。
- 外部ドメインのcanonical値は現在のSite実装では採用しません。Zenn由来記事も公開HTMLはRosariumのURLです。出典を理由に旧Zenn URLを正規URLへ戻しません。
- 元slug、Book/Chapter slug、type、topics、公開日・公開月、URL、元front matterは `source` と移行台帳に保持します。既存の移行元metadataを削除・一括書換えしません。
- 旧GitHub Pages URLは互換入口として扱い、新しい内部リンク・canonical・OGP・サイトマップには正規ドメインを使います。既存URLの廃止や転送変更は別途レビューします。
- 月までしか分からない公開日は月表示を維持します。既存記事の `publication_date_basis: fallback` は過去の運用上の基準であり、史実の公開日や今回の改訂日へ読み替えません。公開日の解決順は `src/lib/publication-date.ts` を参照します。

## 検証と公開

記事本文の修正だけで作業完了と判断しません。新規作成・改訂を完了する前に、次を確認します。変更対象や公開状態により対象外となる項目は、その理由を確認します。

- [ ] 記事本文・概要・図解の整合性
- [ ] `last_updated`の更新要否（Bookは変更した章ごと）
- [ ] `published_at`の維持（改訂で初回公開日を変更していないか）
- [ ] GARDEN NOTESの更新要否
- [ ] 個別記事の更新履歴への反映（対象ID・action・実際の変更内容）
- [ ] 記事カード・前後ページ・検索結果の更新日
- [ ] 内部リンクと公開状態（未公開記事が公開履歴に含まれていないか）
- [ ] 型検査・テスト・ビルド


```sh
npm ci
npm run check
npm test
npm run build
npm run preview
```

`check`はAstroの型・schemaと移行完全性を検証します。`build`は静的HTMLとPagefind索引を生成し、リンクを検証します。
移行済み本文の編集でハッシュ検証が失敗した場合は、意図した本文変更かレビューし、台帳の変更理由とハッシュも同じコミットで更新してください。失敗を無条件に無効化しません。

`master`へpushするとGitHub Actionsが公開します。default branchを`main`へ変更しません。
この公開動作は公開承認を意味しません。記事制作・更新は[AGENTS.mdの必須工程と公開境界](../AGENTS.md#必須工程と公開境界)に従い、ローカル検証 → 既存ステージング反映・動作確認 → レビュー資料提供 → セリーヌレビュー → 指摘修正・必要な再レビュー → 裕太朗の明示承認 → 本番公開・結果確認の順で進めます。ステージング未確認・レビュー未実施・承認前に本番公開を起動しません。
制作完了にはステージングへの実反映とレビュー可能な原稿・PC／スマートフォン画像等が必要です。既存の限定レビュー環境の公開範囲を広げず、利用不能時に本番で代替しません。完了報告はAGENTS.mdの9項目で行い、Codexのセルフレビューとセリーヌのレビューを区別します。
Repository Settings → Pages → SourceはGitHub Actionsに設定します。
Zennとの自動双方向同期は行いません。

## 初回移行の再現

## 文章の段落と行長

段落は文字数ではなく、主張・理由・条件・対比・結果などの意味のまとまりで分けます。「しかし」「そのため」「一方」などで論点が切り替わる場合は、段落を分ける候補とします。同じ主題を説明する短い文はまとめ、1文ごとの分割や大量の`<br>`は避けます。

3項目以上の独立した説明は箇条書きを検討します。短い並列語や、同じ判断に必要な前提は無理に分解しません。見出し直後は節の主題を示し、その後に詳細や判断理由を続けます。

本文幅は日本語の読みやすさとDesktopの余白を両立します。`ch`は日本語の文字数と一致しないため、60〜75chを機械的に適用して本文だけを狭めません。本文全体の上限70remと画面幅を使い、段落間は約1emに保ちます。変更時は文章・数値・リンク・Front Matterを保持し、Mobileでも過剰な分割や余白がないことを確認します。

## 主要事例の理解支援図

主要3事例の読者向け可視化は、SVGとTypeScriptで実装します。`src/data/case-diagrams.ts`でノード・役割・分岐・説明を管理し、本文では`<div data-case-diagram="system-understanding"></div>`のように共通コンポーネントを呼び出します。顧客サポートDXの全体図は既存の専用レイアウトを維持し、選択操作を共通化しています。

人間は破線、AI支援は太線、知識は淡い背景、判断は丸みと強調線、評価・再利用は別背景で表します。色だけに依存しません。JavaScript無効時も静的SVGと説明へのアンカーが残ります。

主要事例の全体図と章ごとの詳細図は、SVG＋TypeScriptを正本とします。旧生成図は置き換え、専用の図記法・レンダラーは使用しません。新しい理解支援図を過去に作成した実物として掲載しません。記事の既存構造図も静的SVGとして表示します。

## 企画・要件定義・DXの判断基準

| 領域 | 中心の問い | 決める内容 |
| --- | --- | --- |
| 企画 | 何を、なぜ、どこまで実現するか | 業務課題、目的・価値、業務要件・業務目標、KPI、対象と対象外、投資・優先順位、刷新・廃止 |
| 要件定義・システムアーキテクチャ | その業務要件をシステムとしてどう実現するか | 機能・非機能要件、利用者との役割分担、方式、評価・テスト・移行・運用 |
| DX | デジタル技術によって何が変わるか | 業務プロセス、価値、組織や仕事の変化 |

企画 → 業務要件・業務目標 → システム要件 → 実現方式を区別します。業務要件・業務目標は企画で決め、システム要件はそれを情報システムとして満たすべき条件へ具体化します。実現方式は、その条件を満たす技術方式です。工数削減や自己解決率の目標を生成AI・RAGという技術名で表現しません。要件は必要な能力・条件として書き、技術はそれを実現する方式として比較します。

PoCという語だけでは分類しません。実施するか、継続判断、費用・期間の上限は企画判断です。比較方式、評価データ、品質条件、合格条件の検証設計は要件定義・システムアーキテクチャです。現場理解・仮説・プロトタイプ・利用者評価による反復でも、この判断の違いを維持します。

### 既存metadataからの導出

`/planning/`は読者目的の横断入口です。`src/lib/planning.ts`で、本文が企画判断を扱う既存の`IT戦略`・`システム企画`・`ECRS`タグから対象知識を導出します。`layer`、`section`、`design_topic`、DXの`primaryCategory`は従来の意味とURLを維持し、`section: planning`や重複する専用metadataは追加しません。タグは本文の中心的な問いを確認して選び、単にKPIやPoCが登場するだけでは企画に分類しません。

Caseはこの知識記事の導出から除外します。企画事例を将来接続するときは、実際に担当した企画判断を確認してCaseの明示的な対応表へ追加します。与えられた業務目標を著者の企画実績に置き換えません。`customer-support-ai-dx`は、企画部門が決めた目標を要件と方式へ具体化したシステム設計事例です。

DXとの関係があれば、同じ知識記事をDXと企画の両入口から参照できます。本文やURLを複製・移動せず、独立した問いがある場合にだけ新規記事を作成します。

## AIトップのカテゴリ内関連記事

`/ai/` の「最初に読む」は既存の代表記事を維持します。カテゴリ内の関連リンクへ掲載する記事には、Front Matterの任意項目 `ai_theme` を明示します。値は `ai-design`（AI設計）、`ai-mathematics`（数学）、`ai-theory`（AI理論）、`knowledge-context`（ナレッジ / コンテキスト）、`evaluation-hitl`（評価・ヒューマンレビュー）、`practices`（実践・開発）のいずれかです。

## 未公開下書きの限定レビュー

`status: draft`かつ`public: false`の記事は、通常の`npm run build`、一覧、検索、フィード、サイトマップへ含めません。日付だけを理由に公開しません。明示承認された公開準備では予定日を設定できますが、draft/public:falseを維持します。

レビュー用に選んだIDだけを別出力へ描画します。

```powershell
node scripts/build-review.mjs
node scripts/verify-review-build.mjs
node scripts/preview-review.mjs
```

検証は通常ビルド`dist/`を先に作ってから行います。レビュー用検索は通常ビルドの公開記事インデックスを再利用し、下書きHTMLを索引化しません。レビュー出力は`dist-review/`です。下書きページはnoindex、内部検索対象外、レビュー用表示付きです。noindexはアクセス制御ではありません。既存のTailnet限定接続でのみ共有し、Funnelや本番へ公開しません。レビュー用環境変数をGitHub Actionsや本番に設定しません。Draft PRをレビューしても公開承認やマージを自動的に行いません。

## 内部分類と読者向けの表示

主要な閲覧領域は、庭、AI、DX、IT戦略・企画、システム設計、事例、キャリアです。論理上の担当領域と新しい入口の参照記事は`src/data/knowledge-domains.mjs`を正本にします。既存の`entry_points`（AI／DX）は横断的な掲載先として維持し、記事の正本・URL・本文を複製しません。一般的な要件・方式・保守の設計と、AI固有の理論・RAG・HITLを区別し、Case・Bookは事例に残します。領域の追加だけで職歴・資格・担当実績を追加せず、記事本文が変わらない分類・共通ナビゲーション変更では記事の更新日を一括変更しません。

`layer`は知識の役割、`section`は既存テーマとURLの分類、`design_topic`はAI設計の技術領域です。`primaryCategory`はDXの主カテゴリ、`publication_format`は公開形式、`tags`は検索・横断的な関連付けに使います。これらの意味を混同しません。

一般の記事カードでは主題を示す既存ラベルを優先し、AI設計は`design_topic`の表示名を用います。DXの掲載カテゴリを全ページ共通の主題ラベルへ流用しません。DX入口・カテゴリ一覧は従来の主カテゴリで掲載します。Book・連載などの公開形式は補助情報です。

記事種別は`src/lib/navigation.ts`の`contentType`で共通判定します。実務事例は既存の事例管理データとその章、仮想設計は`src/data/design-studies.mjs`の明示定義を使います。`kind: case`だけでは実務実績と認定せず、不明なものは「事例」にとどめます。論考・技術解説・参照資料も既存メタデータから表示し、内部管理値や同義ラベルを重ねません。記事ヘッダーと検索の記事種別はこの判定を共有します。検索にはタイトル・概要・種別・最終更新日を示し、内部分類や読む目的の羅列を表示しません。検索に必要な内部メタデータは保持します。

タグの追加前に既存表記を確認し、同義のタグは「生成AI」「AI活用」のように統一します。変更時は抽出・関連表示・検索への影響を確認し、Front Matterと参照コードを整合させます。出典の`source.metadata`は来歴情報として元の値を保持します。表記統一を理由に公開状態や分類値を変えません。

### 継続するステージングレビュー対象

`scripts/review-targets.json`を対象一覧の正本とします。`node scripts/build-review.mjs essays/new-id`は既存対象と追加IDの和集合をビルドし、成功後に追加IDを保存します。次回以降の追加で既存対象を置き換えません。対象の削除は一覧を明示的に編集します。`preview-review.mjs`も同じ一覧からプロセス限定の`ROSARIUM_DRAFT_PREVIEW`を設定します。本番ビルド・公開予約ではこの一覧を読み込みません。

## 文章表示と共通レイアウト

- 通常の文章を一文ごとに分割しません。句点を改行へ置換する処理、文章の位置調整用のbr、本文のwhite-space: pre-line等での固定整形を避けます。意味が切り替わる箇所は段落にします。
- 見出し・箇条書き・表・引用・ソースコード・数式・図解・意味のある整形済みテキストの構造と必要な改行は保持します。すべての改行を一律には削除しません。
- 見た目の折り返しだけの修正で、文字を縮小したりコンテンツ幅を無理に拡張したりしません。主要カテゴリは共通Siteレイアウトとナビゲーションを使い、Careerだけ左サイドバーを外す例外は作りません。
- 強制改行の撤去だけで記事の日付を一括更新しません。Career方針など実質的な編集は既存の日付規約に従います。表示改善はサイト共通の履歴として記録します。
- npm run checkはMarkdown構文に基づいて通常段落の強制改行を検出します。npm run buildは全生成ページの不要なbrも検査します。引用や目次の副題は検出から区別し、コード・数式・表の空白や改行を正規化しません。
