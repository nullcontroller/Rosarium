## 要求と方式を分けて扱う

システムアーキテクトは、事業・企画部門から受けた要求を、必要なシステム能力、機能分担、処理方式、責任境界、評価条件へ具体化する。  
価値発見や予算配分、経営上の優先順位を決める企画判断とは区別する。  
要求に曖昧さや矛盾があれば依頼側へ確認し、技術選択だけで目的を書き換えない。

| 概念 | 決めること | 技術名で置き換えないもの |
| --- | --- | --- |
| 業務目標 | 何を達成したいか | 成果の指標・対象・期限 |
| 業務要求 | 業務をどう変えたいか | 利用者の行動・担当者の仕事 |
| システム要件 | システムが何を満たす必要があるか | 機能・品質・運用の条件 |
| システム方式 | どの構成・処理・機能分担で満たすか | データフロー、境界、異常時の経路 |
| 実装 | 選択した方式をどう構築するか | コード、設定、接続、試験 |
| 評価 | 方式が要求を満たすか | 検証条件、結果、採否の根拠 |

「RAGを使う」は方式の候補であり、業務要求ではない。  
要求と方式を分けることで、別の技術やAIを使わない構成でも同じ条件で比較できる。

## 人間の作業を必要な機能へ分解する

人手が必要な理由を「複雑だから」で止めず、判断の入力・出力・条件を調べる。  
既存の手順、文書、操作、例外処理を確認し、担当者が暗黙に補っている情報を取り出す。

| 人が行う判断・作業 | システムに必要な能力 | 確認する境界 |
| --- | --- | --- |
| 依頼を理解する | 対象と目的を整理する | 解釈と依頼者の原文を区別する |
| 不足情報を見つけ、質問を選ぶ | 追加確認し、得た条件を保持する | 未確認の条件を推測で確定しない |
| 対象条件を確定する | ID・版・利用条件を照合する | 利用可能な情報の範囲を定める |
| 情報を探し、根拠を選ぶ | 適合する範囲から検索・取得する | 類似性と適用資格を分ける |
| 結果を作る | 根拠に沿った候補を生成する | 根拠のない主張や操作を採用しない |
| 解決できない場合に移す | 停止理由と途中情報を引き継ぐ | 次の判断主体を失わない |

分解した機能ごとに、正常終了・入力不足・根拠不足・専門判断の条件を置く。  
一つの「AI機能」にまとめると、どの能力が不足し、誰が判断を引き取るかが見えなくなる。

## 機能と品質条件を対応付ける

機能要件だけでなく、誤りの影響、応答時間、費用、権限、可用性、保守性、追跡可能性を確認する。  
例えば根拠付き回答を求めるなら、文書を取得する機能だけでなく、版・対象・権限を確認し、根拠へ戻れる条件が必要になる。

各要件について、入力、出力、前提、失敗時の分岐、判断主体、評価方法を記録する。  
評価できない要求は、方式を選ぶ前に確認可能な条件へ具体化する。  
非機能条件が競合する場合は、許容範囲と優先する条件を要求側へ確認する。

## 技術方式を比較し、採用理由を残す

| 方式候補 | 得られること | 制約・失敗 | 選択する条件 |
| --- | --- | --- | --- |
| ルールベース処理 | 明示した条件で再現可能に判定する | 分岐の増加とルール更新負担 | 条件と例外を列挙できる |
| 従来型の検索 | ID・語句・条件を指定して取得する | 言い換えや曖昧な入力を取りこぼす | 厳密な対象照合や既知語の探索 |
| ベクトル検索 | 意味的に近い情報を取得する | 別対象の類似文書も取得し得る | 適用条件で対象を制限した上で探索する |
| 生成AI | 柔軟な追加質問、要約、文章候補を作る | 企業固有の事実や権限を保証しない | 必要情報・根拠・停止条件を外から与えられる |
| RAG | 取得文書に基づく生成へつなぐ | 誤った根拠を渡せば誤回答につながる | 取得根拠の適合性と利用を検証できる |
| 既存システムの機能 | 正本、権限、現在状態、確定処理を利用する | 接続・互換性・変更範囲の制約 | 確定値と実行を既存の責務に残せる |
| 人間の確認・判断 | 曖昧な境界や業務上の妥当性を判断する | 待ち時間と確認負荷 | 根拠・時間・権限を持つ担当者へ渡せる |

採用案だけでなく、不採用案とその理由も要件へ対応付ける。  
固定的な処理で満たせる要件へ生成AIを追加する必要はない。  
一方、動的な追加確認が必要な場面を固定フォームだけに任せると、利用者へ分類知識を要求する制約が残る。  
委任する範囲とリスクの判断は[AI適用可否と委任レベルの設計](/foundations/applicability-and-delegation/)を使う。

## 機能の組合せとして方式を設計する

QAは一例であり、文書照合、登録支援、保守支援にも、条件収集・根拠取得・候補生成・採否判断の分離を適用できる。  
以下は実装クラスや製品構成を規定しない概念フローである。

```text
依頼 → 条件収集 → 対象・適用範囲の確定
                        ↓
              根拠の候補範囲を制御 → 検索・取得
                        ↓
                 候補生成 → 検証・採否判断
                        ├─ 条件を満たす → 回答・承認・確定処理
                        └─ 不足・対象外・専門判断 → 追加確認・停止・有人移管
```

| 機能 | 入出力・前提 | 方式・責務 | 失敗時の経路 |
| --- | --- | --- | --- |
| 条件収集 | 原文から必要条件を集める | 対話またはフォームで収集し、システムが保持 | 追加確認、特定不能なら移管 |
| 対象制御と検索 | 適用条件が確定した範囲で取得する | 属性照合と検索機能を分ける | 根拠不足として停止・移管 |
| 候補生成 | 適合する根拠を入力とする | 生成AIまたは既存処理が候補を作る | 根拠外の候補は不採用 |
| 採否・実行 | 検証済み候補、権限、現在状態 | システム検証と人の承認、既存システムの確定処理 | 差戻し、拒否、再確認 |

入力不足のまま検索し、後で文章だけを修正する順序にはしない。  
処理の前提が成立しないときは、正常な別経路として追加確認・停止・移管を選べる構成にする。

構成要素の配置、検索対象制御と根拠の適格性、承認・実行の境界は[参照アーキテクチャ](/architecture/reference-architecture/)に集約する。  
運用のKnowledge更新と失敗の受け取り先は[QAチャット運用思想](/knowledge-context/qa-operations/)を参照する。

## PoCを方式の採否判断へつなぐ

PoCは、候補方式が要求と品質条件を満たせるかを確かめる工程である。  
検証前に、方式の仮説、対象、成功条件、許容できない失敗、判定主体、本格開発へ進む条件を決める。

最終回答の正答率だけでは、対話・検索・生成・移管のどこを変えるべきか分からない。  
工程別の検証方法、専門家へ確認を集中する分担、効果試算と本番実測の区別は[QAチャット評価設計思想](/evaluation-hitl/qa-evaluation/)に集約する。

| 評価で分かったこと | 方式の判断 |
| --- | --- |
| 必須の品質条件を満たし、運用負荷も担える | 適用範囲と残る不確実性を記録して採用候補とする |
| 不適合な文書を取得する | メタデータ・検索対象制御を修正して再評価する |
| 必要な追加質問が不足する | 対話・入力条件・状態保持を見直す |
| 根拠外の回答を生成する | 生成条件・検証・停止条件を見直す |
| 回答不能で業務が止まる | 有人移管と引継ぎ情報を見直す |
| 必須条件を満たせず、改善や確認も成立しない | 当該方式を棄却し、別方式または範囲縮小を検討する |

変更前後の比較条件を保持し、既存の安全な処理を壊していないかも再評価する。  
技術デモが動いたことを、そのまま本番適用の承認にはしない。

## 設計方法と実績の区別

本記事は試験論述用資料から抽出した方法論であり、特定のPoC実施期間・人数・評価率・本番導入を本人の実績として示すものではない。  
原典固有の数値や効果試算は持ち込まず、要求、方式、評価、採否判断の接続を説明している。

要求の目標値、評価データ上の結果、試算、本番の実測値は別々に扱う。  
方式を選ぶ根拠と、実際に担当・確認した成果の範囲を混同しない。
