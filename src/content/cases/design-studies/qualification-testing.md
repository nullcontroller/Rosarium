## このケースで確認する3つの品質

例えば、USB接続の質問にはUSBの手順を返せても、稼働中のネットワーク変更を無条件に勧めてしまうQAシステムでは困ります。マニュアルにない障害へ、もっともらしい原因を答えることも止めなければなりません。

RAGは、文書を検索し、その根拠を使ってAIが回答する方式です。本ケースでは三つの問い合わせを実際に入力する想定で、次を確かめます。

- 答えてよい問い合わせに、根拠に沿って正しく回答できるか。
- 答えてはいけない問い合わせを止め、CS担当者へ引き継げるか。
- 利用者が増えても、十分な速さで処理できるか。

実務PoCでは検索対象制御を改善し、設定目標を達成しました。それだけで業務機能全体や本番相当の性能を確認したことにはならないため、この仮想ケースへ発展させています。

## 3種類の問い合わせと期待する動作

対象はPrinter-Aの第2版です。その製品マニュアルを「文書A」、USB接続の設定手順を「節A」、無線LAN接続の設定手順を「節B」と呼びます。両節は承認済みで、対象製品の版に適用できるものとします。

| ケース | 問い合わせ | 期待する動作 |
| --- | --- | --- |
| Q01：定型 | USB接続の設定手順を知りたい | USB手順を根拠に自動回答。不要な有人引継ぎはしない |
| Q02：専門判断 | 稼働中の共有ネットワーク設定を変更してよいか | 操作手順があっても業務影響は判断できないため、回答を止めてCSへ引き継ぐ |
| Q03：根拠不足 | 無線LANで、文書に記載のない症状が出る | 原因や対処を推測せず停止し、CSから必要に応じて開発確認へつなぐ |

Q01の環境はUSB、Q02・Q03は無線LANです。Q02で関連する手順が見つかることと、変更を勧めてよいことは別です。Q03も、似た症状の文書を取得しただけでは、回答に十分な根拠とはしません。

## 自動回答・停止・有人引継ぎをどう確認するか

### Q01：検索結果と回答内容を確認する

節Aを取得し、製品・版・USBという条件が一致することを確認します。自動回答の許可経路を通っても、無線LANの説明を混ぜたり、根拠にない操作を加えたりすれば不合格です。回答品質と回答可否を分けて判定します。

### Q02・Q03：停止から業務継続までを確認する

| 工程 | 確認すること |
| --- | --- |
| 受付・検索・回答可否判定 | 問い合わせ原文と製品・版・環境を記録し、根拠と適用条件から専門判断または根拠不足を識別する |
| 自動回答の停止 | 確定的な回答や操作指示を顧客へ送らない。受付状況の案内は行える |
| CSへの登録 | 原文、確認済み条件、参照根拠と版、停止理由、未解決事項を渡す |
| CS側の受付確認 | CS側の受付記録と受付IDを照合し、受付結果を返す。送信キューへの投入や引継ぎフラグだけで成功にしない |
| 業務継続の確認 | CSが不足情報を確認し、Q02の影響調査やQ03の開発確認を続けられるかを確認する |

登録失敗や再試行中は受付完了と案内しません。必要な有人対応は失敗ではありませんが、停止しただけで引継ぎまで成功したとは判断しません。

## 自動テストとCSレビューの役割分担

### 機械で照合する項目と、人が判断する内容

| 分担 | Q01〜Q03で確認する例 |
| --- | --- |
| 自動テスト | 文書ID・取得節・製品版・利用環境、回答経路、停止状態、CS受付、引継ぎ必須情報の有無 |
| CSレビュー | Q01の手順が根拠に沿うか、Q02で危険な変更を勧めていないか、Q03で原因を断定せず調査を継続できるか |

全件目視だけでは同じ属性照合を繰り返し、件数が増えると見落としも生じます。一方、AI評価だけでは、Q02の危険な案内を自然な文章として合格にするおそれがあります。そこで、追跡できる属性や経路は機械に任せ、意味の判断にCSの確認を集中させます。AI評価は補助にとどめ、判断できない結果を無理に合格にせず保留へ回します。

### 期待値とデータ版をそろえて実行する

業務機能の確認は夜間に自動実行し、翌朝DX部とCS部が結果を確認する計画にします。

1. 過去1年の問い合わせが18,000件あると想定し、DX部とCS部が500件を選び、期待する検索根拠・回答経路・禁止する案内を定めます。
2. 夜間、テスト用の問い合わせをQAシステムへ送り、分類、検索した文書、回答可否、回答文、引継ぎ結果を記録します。
3. 翌朝、DX部がログと期待結果を照合します。Q01なら文書の製品・版・環境、Q02・Q03なら回答停止とCS受付を確認します。
4. 過去の正解回答との意味の一致を確実に判定できない結果は保留にします。CS部が回答の妥当性と、引継ぎ後に対応を続けられるかを確認します。

例えばQ02の受付が成功していても、受渡し情報に変更対象のネットワークがなければ、CS担当者は影響調査を続けられません。受付ログだけでなく、担当者が受付画面で何を確認できるかも試します。

過去の正解回答も、対象条件と参照文書が今も有効かを確認して使います。コピーや自由文の完全一致だけで合否は決めません。

500件は通常例だけで埋めず、似た製品、異なる版、条件不足、文書の矛盾、引継ぎ失敗を含めます。分類別の件数と選定条件を残し、同じ検索データ版・モデル・設定で実行します。生成の変動を見る複数回の試験では、回数と判定方法を先に決め、都合のよい一回だけを選びません。

## 50人同時利用を想定した性能テスト

例えば1,000件を送信する場合、950件以上が10秒以内に正常完了すれば、設定した応答性能の条件を満たします。

仮想条件は**50人同時利用で、全要求の95％以上が10秒以内に正常完了すること**です。エラー、タイムアウト、誤った自動回答、引継ぎ受付失敗は正常完了に含めません。10秒を超えた要求も、この条件の分子には含めません。

計測は要求の送信開始から始めます。Q01は回答の受信完了まで、Q02・Q03は回答停止とCS受付結果の受信完了までを測ります。CS担当者が調査して最終回答するまでの時間は、この10秒に含めません。品質の合否はCSレビュー後に確定し、試験時の応答時間とは分けます。レビュー待ちを成功扱いせず、レビューの待ち時間も応答時間へ加えません。

検索対象が少ない段階の測定では、文書・節・属性が増えた後の負荷を見込めません。業務機能の確認後に、想定する検索用データ量と構成を固定して性能を評価します。同時利用者数に加え、要求間隔・Q01〜Q03の構成比・継続時間もそろえます。検索データの版、モデル・設定、キャッシュ条件も記録します。

## 不合格になったときの原因調査

| 不合格の例 | 原因を追うために残す記録 |
| --- | --- |
| Q01でUSB手順ではなく別の節を取得した | ケースID、問い合わせ条件、検索条件、取得節と版、検索データ版 |
| Q02で停止すべき操作指示を送った | 回答可否判定、停止理由、回答文、根拠との対応 |
| Q03でCS受付に失敗した | 引継ぎ先の受付結果、受渡し情報、処理状態 |
| 応答が10秒を超えた | クライアントの計測値と、検索待ち・API待ち・生成・CS受付の時間内訳 |

全体の正答率だけでなく、検索根拠、回答可否、回答内容、引継ぎ受付、業務継続のどこで不適合になったかを分けます。検索が遅いのに生成だけを調整する、といった取り違えを避け、対策後も同じデータ量・負荷条件・計測区間で再テストします。ログは確認に必要な範囲に限定し、閲覧権限と保存期間を定めます。

## 設計判断のまとめ

回答の正しさと回答してよいかを分け、属性・経路の自動照合とCSの業務レビューを組み合わせます。回答停止と引継ぎ受付は個別に確認し、担当者が対応を続けられることまで確かめます。性能は想定する検索データ量に近い条件で評価します。
