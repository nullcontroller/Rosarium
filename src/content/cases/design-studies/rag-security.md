## 顧客向けAIに、社内報告書を読ませない

例えば、顧客から「無線LANで印刷できない」と届いたとします。製品情報システムには、公開済みの復旧FAQと、同じ障害の未公表原因を調べた社内報告書があります。従来のCS担当者は両方を読み、顧客へ伝えてよい内容だけを選んでいました。

この二文書を区別せずAIへ渡すと、社内報告書の内容が回答へ混ざるおそれがあります。RAGは関連文書を検索してAIの回答根拠にする方式ですが、質問に近いことと公開してよいことは別です。

公開承認済みの文書だけを顧客向け検索DBへ連携し、QAシステムから社内原本を読めないようにします。回答を作った後の検査だけに頼らず、情報を取得する経路で境界を設けます。

実務事例では、根拠の取得と自動回答の許可を分けました。本ケースはその区別を公開範囲へ広げ、FAQと社内報告書が混在する仮想条件を置いたものです。

## 同じ症状を説明する、公開FAQと社内報告書

顧客が「Printer-Aで無線LAN印刷ができない」と質問した場面を考えます。

| 文書 | 内容と公開状態 | 顧客向け検索への扱い |
| --- | --- | --- |
| faq-001 / v2 | 顧客へ案内できる復旧手順。対象版を公開承認済み | 連携できる |
| report-001 / v2 | 同じ症状の未公表原因と調査経緯。社内向け | 連携しない |

両文書は意味的には質問と関連します。そのため、関連度が高い順に検索するだけでは、社内報告書を選ぶ可能性があります。製品・版・利用環境を示すメタデータ（検索用の属性）が一致しても、公開してよい根拠にはなりません。

本ケースでは、原本システムが文書の版ごとに公開承認を管理できることを前提にします。扱うのは全顧客へ共通に公開できる情報です。顧客別の契約情報を扱う場合には、さらに顧客・権限単位の認可が必要です。認可は、その利用者やシステムに情報を読む許可があるかを確認することです。

## 公開承認を確認してから、検索用DBへ渡す

<div data-case-diagram="design-study-security-boundary"></div>

1. 原本システムでFAQと社内報告書を管理する。CSは許可された範囲で両方を調査できる。
2. 連携処理が文書ID・版・公開区分・承認状態を確認する。未承認・区分未設定は許可しない。
3. faq-001だけを取り込み、節へ分割する。検索用属性のレビュー後、公開用DBへ登録する。
4. QAシステムは公開用DBだけを検索し、取得したFAQを根拠に回答する。
5. 公開根拠が足りない場合や専門判断が必要な場合は回答を止め、CSへ引き継ぐ。

report-001は連携段階で除きます。QAには公開用DBを読む権限だけを与え、社内原本の読取りや索引への書込みを許しません。CSが社内資料を調査する経路は顧客向けAIと分け、引継ぎには確認済み条件、公開根拠、停止理由、未解決事項を渡します。

## なぜ回答後の検査や検索フィルタだけでは足りないのか

社内報告書をAIへ読ませた後で機密表現を消そうとしても、言い換えによる漏れを防ぎきれないおそれがあります。一度渡した情報を、出力検査で必ず回収できるとは考えません。

共通の検索DBを公開区分で絞る方式もあります。ただし、条件の付け忘れや広すぎる権限があると社内文書を取得できます。本ケースは、公開承認の確認、公開用DB、取得権限を組み合わせる方式を採用します。検索時のフィルタや出力検査は補助として使い、単独の防御にはしません。

この方式には、連携や公開取消しを継続管理する負担があります。また、公開承認自体の誤りは防ぎきれないため、内容を確認する担当者の役割も残ります。

## FAQが改訂・公開取消しになったらどうするか

例えば、公開済みFAQの復旧手順へ、開発担当者が未公表の原因分析を追記したとします。v2が公開済みでも、v3へ承認を自動継承すれば、その追記も顧客向けAIへ渡ってしまいます。そこで改訂版を未承認に戻し、権限を持つ製品担当者が変更内容を確認して再承認するまで連携しません。レビュー画面には追記箇所と前後の説明を示します。ただし、承認する対象は差分だけでなく、その追記を含む改訂版全体の公開可否です。連携処理は承認された文書ID・版と、取得する本文の版が一致するかを確認します。

公開承認と、検索属性が本文に合うかのレビューは別の判断です。両方を必要とする構成では、公開可でも属性が未確定なら検索へ反映しません。

公開を取り消した版は索引・キャッシュから除外します。反映に時間差がある場合も、回答提示前の有効性確認で使わせません。取消し前に提供した情報まで完全に回収できるとはしません。

## 情報の境界をどうテストするか

「無線LANで印刷できない」を入力する前に、連携対象一覧でfaq-001だけが登録されているか確認する計画です。問い合わせ実行時には、検索結果と生成AIへ渡した根拠にreport-001が含まれないことを確認します。画面の回答が安全に見えるだけでは合格にしません。

| 条件 | 期待する結果 |
| --- | --- |
| FAQは公開承認済み、報告書は社内向け | FAQだけが連携・取得される |
| 区分未設定・未承認の文書 | 連携しない |
| FAQのv3が未承認 | v2の承認を継承せず、新版は取得させない |
| 承認取消し直後に同じ問い合わせ | 古い索引・キャッシュに残っても回答根拠として使わない |
| 公開根拠だけでは回答不能 | 社内原本を追加取得せず、CSへ引き継ぐ |
| QAの資格情報で社内原本へアクセス | サーバー側で拒否される |

ログは文書ID・対象版・許可／拒否・取得先を追えるようにし、内容の保存範囲・閲覧権限・保存期間を定めます。検査データの原文を無制限に記録する前提にはしません。

## まとめ

社内情報を顧客へ出さないために、公開FAQだけを連携し、QAが読める取得先も限定します。検索への適合性、公開承認、版の有効性を別々に管理し、公開根拠がなければ人へ渡す設計です。
