**導入後も、何が失敗し、誰が直し、どの条件で反映するかを追跡できる運用を設計しました。**  
回答率だけでなく、有人対応の負荷や重複質問も確認対象に含めています。

## 導入を完成にしない

問い合わせの内容、対象製品、回答に使う参照資料、利用者の入力は変化します。  
PoC時点で回答できたからといって、同じ品質が続くとは限りません。

運用では、正解率や自己解決率だけでなく、どこで利用者が操作をやめ、なぜ担当者へ引き継ぎ、どの資料が不足していたかを確認する計画です。

## 観測するもの

| 観測対象 | 改善を検討する箇所 |
| --- | --- |
| 誤った回答・根拠にない説明 | 回答の条件、AIへの指示文、顧客へ提示してよいかの確認方法 |
| 有人対応へ移った問い合わせ | 自動回答の対象、停止条件、担当者との業務分担 |
| 適合する文書を取得できない | 参照資料の追加、機種・版との対応付け、検索条件 |
| 追加質問が長い・利用者が途中でやめる | 質問の順序と表現、画面や入力支援 |
| 同じ確認を担当者が繰り返す | 引き継ぐ情報、担当者向け画面、確認済み事項の要約 |
| 新機種の追加・版数の更新 | 資料の有効期間、変更後にも従来の回答を確認する評価データ |

確認する品質を、AIの出力、システムの動作、業務上の成果へ分けます。

| 確認する品質 | 確認すること | 見直す箇所 |
| --- | --- | --- |
| AIの質問と回答 | 質問が必要情報を得られるか、回答が根拠と整合し裏付けのない内容を含まないか | 指示文、AIに渡す情報、回答の生成条件 |
| システムの動作 | 適合する文書を取得できるか、遅延や失敗がないか、停止から引継ぎへ進めるか | 検索条件、条件照合、対話、引継ぎ、監視 |
| 業務上の成果 | 自己解決、有人対応の負荷、再問い合わせ、途中離脱、顧客の利用しやすさ | 自動回答の範囲、業務分担、画面、参照資料の管理 |

一つの数値へ集約しないのは、回答が正しくても、追加質問が長く途中離脱が増えれば業務上の効果が得られないためです。  
逆に自己解決率だけを上げようとすると、停止すべき問い合わせまで回答する危険があります。

## 失敗を分類して改善する

回答できなかった問い合わせを、すぐ参照資料の不足と決めつけません。  
資料が存在しない場合と、資料はあっても使えない場合では、直す場所が異なります。

- 必要な資料が存在しない
- 資料はあるが、対象機種・版数・公開範囲の情報が不足している
- 検索条件や資料の分類が適切でない
- 追加質問で必要な顧客情報を得られていない
- 回答生成が、採用した根拠を正しく利用していない
- 専門担当者が扱うべき問い合わせへ自動回答しようとしている

**失敗原因を工程へ戻し、参照資料・検索・回答許可・業務分担のどこを直すかを分けました。**  
モデルの変更だけで対応しようとせず、問題が起きた工程を切り分けます。

## 変更単位と責任者を分ける

設計・開発側は検索や処理方式、文書管理側は資料とその適用条件、CS部は専門対応と自動回答の範囲を見直します。  
**変更の採否は、設計側と業務側が再評価の結果を確認して判断する運用としました。**

| 問題が起きた箇所 | 何を変更するか | 改善したと判断する条件 |
| --- | --- | --- |
| 参照資料が不足している・情報が古い | 文書管理側が必要な資料を追加し、版数・有効期間・公開範囲を更新する | 対象機種と版数に適合する有効な文書を取得でき、古い情報を回答根拠にしない |
| 適切な資料を検索できない | 設計・開発側が検索条件と検索方法、結果の順位付け、文書の分割方法を見直す | 必要な文書へ到達でき、従来正しく検索できた問い合わせも引き続き処理できる |
| AIの回答が参照資料の内容から外れる | 設計・開発側がAIへ渡す情報・指示文・回答の制限条件を見直す | 回答の各説明を採用した根拠へ対応付けられ、裏付けのない内容が含まれない |
| 利用者が途中で操作をやめる | 設計側とCS部が質問順序・説明・入力支援を見直す | 必要情報を得られ、質問や操作の負担を増やしていないことを利用記録で確認できる |
| 担当者への情報の引継ぎが不十分 | 設計・開発側とCS部が引継ぎ項目・担当者向け画面・引継ぎ後の処理の流れを見直す | 担当者が確認済み事項と未解決事項を区別し、同じ質問を繰り返さず調査を続けられる |
| AIが回答してはいけない問い合わせまで回答する | CS部が回答項目の許可・適用条件・専門判断条件を見直し、設計・開発側が照合と停止条件へ反映する | 自動回答を許可した問い合わせだけに回答し、専門判断が必要な場合は調査結果を担当者へ引き継げる |

CS部と設計側は、検索対象のメタデータと回答項目の許可を別々に管理します。  
検索範囲の誤りと回答許可の誤りを区別し、再評価では定型回答の成立と専門判断・根拠不足時の停止をともに確認します。

## 同じ条件で再評価する

改善後は、失敗した問い合わせを評価データへ加え、比較する条件を揃えて再実行します。  
自動回答の範囲を広げる場合も、従来正しく回答・停止できたケースが変更後も成立するかを確認します。

モデル、指示文、参照資料、検索用の索引、業務ルール、画面の版を一つの組合せとして記録します。  
どの組合せで評価したかを残し、変更前後の差と、問題が起きた場合に戻す対象を追跡できるようにします。

設計側と業務側が基準を満たすと判断した変更だけを反映し、停止漏れや重大な品質低下があれば適用範囲を戻す計画です。

導入後の計測では、引継ぎ後の対応工数、確認済み事項の重複質問、再問い合わせも評価対象にします。  
参照資料の新規登録、機種追加、版数変更、回答許可の見直しごとに再評価し、業務負荷が増えていないかを確認します。  
これらは導入後の運用設計であり、既に運用効果を測定した成果とは扱いません。

設計、利用、利用結果の記録、原因分析、改善、再評価をつなぎ、導入後も見直せる仕組みにします。  
この考え方は[導入から運用・継続改善までの設計](/ai-design/lifecycle-operations/)へつながります。
