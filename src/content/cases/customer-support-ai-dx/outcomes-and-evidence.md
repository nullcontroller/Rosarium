## 設計した変化の中心は業務構造にある

このケースで設計した中心的な変化は、生成AIを加えることではありません。すべての問い合わせを人間が最初から処理する構造を、自己解決できる問い合わせと専門判断が必要な問い合わせへ分けることです。以下は公開実績のBefore / Afterではなく、統合元資料から整理した現状と設計後の状態を対比しています。

| Before | Afterとして設計した状態 |
|---|---|
| 全件を担当者が受付 | 顧客が自然な言葉で直接問い合わせる |
| 人が不足情報を確認 | AIが定型的な不足情報を確認する |
| 人が複数資料を検索 | RAGが条件に適合するKnowledgeを探す |
| 人がすべて回答 | 根拠とリスク条件を満たす場合だけ自己解決へ進む |
| 解決できない場合も確認をやり直す | 確認済み情報と根拠を人間へ引き継ぐ |
| 改善が個別対応に閉じる | 失敗をKnowledge、Retrieval、UI、業務へ戻す |

この構造によって、顧客の待ち時間を短くすることと、担当者を専門的な仕事へ集中させることを同時に目指します。実際の変化を成果として扱うには、後述する一次情報による確認が必要です。

## 数値を成果として断定しない

統合元の論述資料には、同じ事例について次の数値が記載されています。しかし、公開実績として確認できる一次記録は今回の資料に含まれておらず、資料間で母数や時点も統一されていません。

| 資料に現れる数値 | 本書での扱い |
|---|---|
| 月約1,500件、8名、月約400時間 | 業務規模を説明する論述上の前提。公開実績として未確認 |
| 過去約18,000件の分析 | 適用範囲を決める分析モデル。分析記録は未確認 |
| 400時間から300時間以下 | PoCと採用判断の目標条件 |
| 過去問い合わせ500件 | PoCの評価サンプルとして記述。実施記録は未確認 |
| 約60% | 一資料にある「回答できる可能性」の表現 |
| 全体の約48% / 対象区分の96% | 他資料にある再評価結果。母数が異なるため同一指標として統合しない |
| 400時間から280時間 | 月120時間削減を前提にした試算、または一資料の採用後評価。公開実績として未確認 |

したがって、本書では「月120時間削減した」「自動回答率48%を達成した」と職務実績としては表現しません。数値から採用できるのは、目標から必要な自己解決範囲を逆算し、PoCの受入条件を決める方法です。

## 成果を確認するために必要な証拠

実績として扱うには、少なくとも次の一次情報が必要です。

- 期間と母数が明確な問い合わせ件数
- 自己解決、有人移行、離脱の定義と集計
- 導入前後で比較可能な対応工数
- 回答品質と根拠適合性の評価記録
- 高影響の誤回答や再問い合わせを含む品質指標
- 対象機種、利用者、運用条件の範囲

設計判断と実績を分けることで、ケーススタディの価値を損なわず、事実以上の成果を主張することを避けます。

## 成果は三つの層で確認する

本番導入後の成果を確認する場合は、設計どおり動いたか、業務が変わったか、価値が生まれたかを分けます。

1. **System Outcome** — 適合する根拠を取得し、停止条件とHandoffが設計どおり動いたか
2. **Business Outcome** — 自己解決、有人対応、再問い合わせ、担当者の調査負荷がどう変わったか
3. **Value Outcome** — 顧客の解決時間や体験、専門判断へ割ける時間など、狙った価値へつながったか

この三層をつなぐ一次記録が揃って初めて、設計条件や試算を成果へ更新できます。それまでは、設計した変化と確認済みの実績を同じ言葉で表しません。
