## 担当範囲と事例の主題

企画部門から業務改善の提案を受け、システムアーキテクトとして、業務目標をシステム要件、機能分担、処理方式、責任境界、評価条件へ具体化しました。

現行は、専用の問い合わせ支援システムがなく、担当者が仕様書・FAQ・障害情報を調べ、顧客への追加確認と回答を行う業務です。  
不足情報の追加確認と、対象に適合する回答根拠の判断に人間が介在するため、顧客だけでは定型問い合わせを完結できません。

<div data-case-diagram="support-executive-summary"></div>

回答可能ならQAシステムが顧客へ回答し、根拠不足・原因未特定・専門判断が必要なら、収集した情報と調査結果をサポート担当者へ引き継ぎます。  
担当者は未解決事項から専門調査を続け、顧客へ回答します。  
一次調査の続きを引き受けるため、有人対応も自動回答と並ぶ通常の処理経路として設計しました。

顧客向けQAを新規開発する方式として、要件分析、第1回PoCでのフィージビリティ確認、QAシステム開発、第2回PoCでの問題発見、参照資料整備・停止条件の強化、PoC再実施による評価目標の達成へつなぎます。  
既存の製品資料は、QAが回答に使う参照資料として整備します。

以下は、業務目標を受けて定めた初期構想です。機能が動作することと、業務上の振り分けが十分に機能することは、段階を分けて確認します。

## 何を設計したケースか

| 必要な機能 | 方式と責務 |
| --- | --- |
| 顧客が直接問い合わせる | Web QAで自然言語の問い合わせを受ける |
| 不足情報を集める | 生成AIが顧客の回答に応じて追加質問する |
| 関連する根拠を探す | ベクトル検索で製品仕様書・FAQ・障害情報を取得する |
| 根拠から回答する | 取得文書を与えたRAGで回答を生成する |
| 自動対応を続けない条件を扱う | 根拠不足・原因未特定・専門判断では人間へ引き継ぐ |
| 方式を確認する | 基本動作の確認を経て開発し、システムの評価へ進む |

## 方式設計の判断

**追加質問・文書検索・根拠付き回答を組み合わせ、定型回答と人間による専門対応を分担します。** 自動回答できない問い合わせは、途中で得た情報を担当者へ渡して対応を続ける構想です。

## 設計と評価の進め方

業務要求と初期の役割分担を整理し、フィージビリティ確認からQAシステムの開発へ進みます。[第07章](/cases/customer-support-ai-dx/poc-effect-evaluation/)で開発したシステムを評価し、第08・09章で方式を改善した後、[第10章](/cases/customer-support-ai-dx/poc-metadata-improvement/)で再評価と業務効果の見込みを示します。
