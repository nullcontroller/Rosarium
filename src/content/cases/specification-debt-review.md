## 背景

長期間保守されてきたソフトウェア製品のWord仕様書群をMarkdownへ移行した。移行後の仕様書は68ファイル、元仕様書の総ページ数は約30,000ページだった。本Caseでは、その仕様書群をAIと人間がレビューした過程を扱う。

中心にあるのは、AIへ仕様の正解を決めさせることではない。人間が仕様判断するための探索・比較・Evidence収集をAIへ委任し、判断材料を揃えるレビューである。製品やコマンドの固有情報は示さず、確認できた設計判断と結果を記述する。

## 最初の目的はMarkdown移行レビューだった

当初は、WordからMarkdownへの変換によって情報欠落、表崩れ、参照切れ、記述差異が発生していないかを確認することが目的だった。変換前後を照合し、文書として情報が保持されているかを調べるレビューである。

しかし、変換結果だけを見直しても、元の記述が現在も有効かどうかは分からない。変換が正確であっても、古い仕様記述をそのまま引き継ぐ可能性があった。

## Documentation Debtが見つかった

レビューでは、誤字脱字だけでなく、古い記述、前提の変化、古いOS環境に関する説明、ファイル間・章間の不整合、同じ対象に対する異なる説明が見つかった。現在も有効か判断が必要な仕様や、実装との不整合も調査対象になった。

これらは変換時に生じた問題だけではない。長期保守の間に仕様Knowledgeへ蓄積したDocumentation Debt、すなわち文書の更新や整合確認が追いついていない状態だった。

そこで問題を「変換品質の確認」から「大量の仕様Knowledgeと現在のソフトウェアとの整合を調査すること」へ捉え直した。形式を移すだけでなく、記述を維持するか、修正するかを判断するための調査が必要になった。

## 68ファイル・約3万ページを照合する難しさ

一つの章を読むだけでは、別の仕様書にある条件や同じ設定項目の説明との差異は見えない。関連仕様を探し、現在の実装を確認し、条件や参照を突き合わせる必要がある。

従来の流れは、人間が大量の仕様書を読み、問題を探索し、他の仕様書と比較し、ソースコードを調査した後に仕様判断と修正を行うものだった。今回のレビューでは、このうち探索・検索・比較・根拠収集をAIへ移し、人間が判断すべき論点を確認できる形にした。

## なぜ仕様書だけをAIへ渡さなかったか

仕様書同士を比較すれば記述の差異は見つけられる。しかし、機能が現在も存続しているか、互換性のために古い処理が残っているか、説明の削除漏れがあるかは、文書だけでは十分に判断できない。

現在のソースコードは、動いているソフトウェアを理解するための非常に強いContext / Evidenceである。ただし、Implementation = Correct Specificationとは扱わなかった。実装が仕様に追従していない可能性や実装Bug、互換性維持の処理、仕様が将来状態を示す可能性がある。コード外の業務・製品条件も判断に関わる。

Documentation、Implementation、変更の経緯、運用・互換性条件を複数のEvidenceとして扱い、どれか一つを無条件の正解にはしなかった。

## 仕様書と現在のコードを同じContextで調査する

Markdown化した仕様書をGit管理し、現在のソースコードと同一開発Project内の関連情報を、AIが同じ開発Contextから参照できる状態にした。MarkdownやGitを採用したこと自体より、判断に必要なEvidenceへアクセスできることが重要だった。

AIは関連仕様、関連コード、同一設定項目、条件、参照、重複を横断して探索した。レビューを「文書同士の比較」から「DocumentationとImplementationの横断調査」へ広げたのである。

AIを選ぶことはモデルを選ぶことだけではなく、どのContextへアクセスさせるかを設計することでもある。この考え方は[AIを使い分ける基準は、モデル性能よりコンテキストではないか](/knowledge-context/context-before-model-performance/)にもつながる。

仕様書・現在のコード・関連ContextをAIが横断調査し、問題候補とEvidenceを整理する。最終的な変更判断は、人間がBefore / Afterを確認した上で行う。追加調査の経路は判断を保留して根拠を集め直す場合を示し、実施件数を示すものではない。

## AIへ任せたこと、人間へ残したこと

AIへ委任したのは、誤字脱字・古い記述・矛盾・重複・参照不整合の候補探索、同じ設定項目の記述差異や章をまたいだ条件不一致の調査だった。仕様書と現在の実装の不整合候補を探し、関連仕様・関連コードのEvidenceを集め、論点を分類して修正候補を提示する役割も担った。

人間へ残したのは、Evidenceの妥当性確認、仕様判断、変更の採否、承認と仕様責任である。AIは仕様を決定しない。Decision Automationではなく、Decision Preparationを委任した。

AI活用後の流れは、横断探索、問題候補抽出、関連仕様・実装の提示、論点分類、修正候補提示、人間によるEvidence確認、Before / After比較、仕様判断、承認した内容の反映となった。人間をなくしたのではなく、調査と変更判断の責任を分けた。

## Before / Afterを人間が確認する

AIの出力をそのまま仕様書へ反映することはしなかった。Beforeは現在の仕様記述、Afterは修正候補として、人間が両者と根拠を比較した。

確認したのは、意味が変わっていないか、現在の実装と整合するか、他仕様との矛盾がないか、互換性条件を壊さないか、コードだけでは把握できない事情がないかである。正しそうに見える変更も、この確認を経て採否を決めた。

Change Proposal → Human Change Validation → Specification Decisionという責任工程であり、人間のレビューは最後の形式的な確認ではない。[AI出力の責任境界とHITL](/evaluation-hitl/responsibility-and-hitl/)を、仕様変更の採否判断として具体化した工程である。

## 実際に見つかったもの

レビューで確認した問題は約40件だった。すべてが修正対象だったわけではない。AIが提示した問題候補を人間が確認し、修正するものと現状維持するものを判断した。

具体例として、ある仕様書で特定コマンドの説明内容に誤りが見つかった。AIが関連仕様と現在の実装を横断調査し、記述と実装の差異を問題候補として提示した。

人間が該当仕様、関連仕様、現在の実装、修正前の記述、修正後候補を確認し、仕様書側の記述誤りと判断して修正した。ここで公開するのは確認の流れであり、コマンド名、Syntax、内部実装は示さない。

## AIの提案を採用しなかったもの

コードだけを見ると変更した方がよく見える記述でも、人間が確認した結果、コード外の事情、互換性、製品条件、保守上の理由から修正すべきではないと判断した箇所があった。

不整合の発見と変更の必要性は同じではない。差異があることを調査の起点とし、その差異を残す理由があるかを確認した。AIはChange Candidateを提示し、Change Decisionは人間が行った。

## 確認できた結果と限界

68ファイル、元仕様書約30,000ページを対象としたレビューで約40件の問題を確認し、実際の仕様誤りも発見した。関連仕様と実装を判断材料として提示し、人間が修正と現状維持を選ぶレビューを行った。

ただし、レビュー前後の所要時間を比較できていないため、工数削減率や短縮時間は示せない。探索負荷をAIへ移したことと、どれだけ時間が減ったかは別の評価である。

- 約40件は修正件数ではなく、レビューで確認した問題数である。
- AI検出のRecall / Precisionは厳密に測定していない。見落としがないとは言えない。
- コードだけでは判断できない仕様が存在する。
- AIの指摘にはHuman Validationが必要であり、もっともらしさだけでは採用できない。
- 時間比較とAIによる工数削減率は未測定である。ROIは推測しない。

## この事例から得た設計原則

1. **MigrationをInspection Opportunityとして利用する。** 形式移行をコピーで終えず、既存KnowledgeのDebtを点検する機会として扱う。
2. **単一Sourceを絶対視しない。** DocumentationもCodeもEvidenceであり、差異があるときは履歴や運用・互換性条件も確認する。
3. **AIへDecisionではなくInvestigationを委任する。** 不確実な仕様の最終判断ではなく、候補抽出と根拠収集を任せる。
4. **モデル性能だけでなくContext Reachを設計する。** 必要なEvidenceへのアクセス範囲を設計し、調査できる条件を整える。
5. **Human Reviewを明確な責任工程にする。** Before / Afterと根拠を比較し、変更を承認する工程として位置付ける。
6. **AIの指摘と変更判断を分離する。** Issue Candidate ≠ Change Decisionであり、現状維持も判断結果になる。
7. **Legacy MaintenanceではDocumentationも保守する。** コードだけでなく、仕様Knowledgeの整合と有効性も保守対象に含める。

このCaseでAIへ任せたのは、判断そのものではなく判断の準備だった。仕様を変える責任を人間へ残し、その判断に必要なEvidenceを探索・比較できる状態を作った。
