## 背景

長期間保守されてきたソフトウェア製品のWord仕様書群をMarkdownへ移行した。移行後の仕様書は68ファイル、元仕様書の総ページ数は約30,000ページだった。分割されたMarkdownをPythonで統合し、GitHub Copilotによるレビューと人間による確認・判断・修正を組み合わせた。本Caseでは、その実務の進め方を扱う。

中心にあるのは、AIへ仕様の正解を決めさせることではない。人間が仕様判断するための探索・比較・Evidence収集をAIへ委任し、判断材料を揃えるレビューである。製品やコマンドの固有情報は示さず、確認できた設計判断と結果を記述する。

## 最初の目的はMarkdown移行レビューだった

当初は、WordからMarkdownへの変換によって情報欠落、表崩れ、参照切れ、記述差異が発生していないかを確認することが目的だった。変換前後を照合し、文書として情報が保持されているかを調べるレビューである。

しかし、変換結果だけを見直しても、元の記述が現在も有効かどうかは分からない。変換が正確であっても、古い仕様記述をそのまま引き継ぐ可能性があった。

## Documentation Debtが見つかった

レビューでは、誤字脱字だけでなく、古い説明、仕様の説明ミス、仕様書間の矛盾が見つかった。

- **古い説明：** 現在では使われていない環境として、Windows 2000に関する記述が残っていた。ただし、古いことだけを理由に削除せず、互換性や過去仕様との関係を人間が確認した。
- **仕様の説明ミス：** あるコマンドの説明内容に、単なる誤字ではなく仕様の意味に関わる誤りがあった。確認と修正の流れは後述する。
- **仕様書間の矛盾：** 複数の仕様書・章で、同じ対象の条件が一致しない箇所があった。どちらの記述が有効か、現在の実装との関係も含めて確認が必要だった。

これらは変換時に生じた問題だけではない。長期保守の間に仕様Knowledgeへ蓄積したDocumentation Debt、すなわち文書の更新や整合確認が追いついていない状態だった。その中には、実際の仕様説明の誤りも含まれていた。

そこで問題を「変換品質の確認」から「大量の仕様Knowledgeと現在のソフトウェアとの整合を調査すること」へ捉え直した。形式を移すだけでなく、記述を維持するか、修正するかを判断するための調査が必要になった。

## 68ファイル・約3万ページを照合する難しさ

一つの章を読むだけでは、別の仕様書にある条件や同じ設定項目の説明との差異は見えない。関連仕様を探し、現在の実装を確認し、条件や参照を突き合わせる必要がある。

仕様書が複数ファイルへ分かれていると、全体像、重複、不整合、参照関係、表記揺れを追いにくい。AIへ横断レビューを依頼する場合も、必要なContextが分散したままでは、比較すべき記述を参照しにくいという問題がある。

従来の流れは、人間が大量の仕様書を読み、問題を探索し、他の仕様書と比較し、ソースコードを調査した後に仕様判断と修正を行うものだった。今回のレビューでは、このうち探索・検索・比較・根拠収集をAIへ移し、人間が判断すべき論点を確認できる形にした。

## なぜ仕様書だけをAIへ渡さなかったか

仕様書同士を比較すれば記述の差異は見つけられる。しかし、機能が現在も存続しているか、互換性のために古い処理が残っているか、説明の削除漏れがあるかは、文書だけでは十分に判断できない。

現在のソースコードは、動いているソフトウェアを理解するための非常に強いContext / Evidenceである。ただし、Implementation = Correct Specificationとは扱わなかった。実装が仕様に追従していない可能性や実装Bug、互換性維持の処理、仕様が将来状態を示す可能性がある。コード外の業務・製品条件も判断に関わる。

Documentation、Implementation、変更の経緯、運用・互換性条件を複数のEvidenceとして扱い、どれか一つを無条件の正解にはしなかった。

## 分割された仕様書を横断レビューできる形へ整える

Markdown化には、検索性、差分管理、分割管理に加え、AIが参照・比較しやすい形へKnowledgeを構造化する意味があった。形式を変えるだけでモデルの能力が上がるわけではない。関連する説明や条件を、レビューで参照できる状態へ整えることが重要だった。

そこで、分割されたMarkdownを1ファイルへ統合するPythonスクリプトを作成した。仕様書全体をAIへまとめて渡し、ファイルをまたいだ重複、不整合、参照関係、表記揺れ、条件差、古い説明を確認しやすくするためである。Pythonそのものではなく、横断調査に必要な情報を一つのContextへ再構成したことが設計上の要点となる。

## 仕様書と現在のコードを同じContextで調査する

Markdown化した仕様書をGit管理し、現在のソースコードと同一開発Project内の関連情報を、AIが同じ開発Contextから参照できる状態にした。MarkdownやGitを採用したこと自体より、判断に必要なEvidenceへアクセスできることが重要だった。

この環境でGitHub Copilotを使い、統合した仕様書と関連コードを参照しながら、同一設定項目、条件、参照、重複を横断レビューした。レビューを「文書同士の比較」から「DocumentationとImplementationの横断調査」へ広げたのである。

AIを選ぶことはモデルを選ぶことだけではなく、どのContextへアクセスさせるかを設計することでもある。この考え方は[AIを使い分ける基準は、モデル性能よりコンテキストではないか](/knowledge-context/context-before-model-performance/)にもつながる。

統合した仕様書・現在のコード・関連ContextをAIが横断調査し、問題候補とEvidenceを整理する。最終的な変更判断と修正は、人間がBefore / Afterを確認した上で行う。追加調査の経路は判断を保留して根拠を集め直す場合を示し、実施件数を示すものではない。

## AIへ任せたこと、人間へ残したこと

AIへ委任したのは、誤字脱字・古い記述・矛盾・重複・参照不整合の候補探索、同じ設定項目の記述差異や章をまたいだ条件不一致の調査だった。仕様書と現在の実装の不整合候補を探し、関連仕様・関連コードのEvidenceを集め、論点を分類して修正候補を提示する役割も担った。

人間へ残したのは、Evidenceの妥当性確認、仕様判断、変更の採否、承認と仕様責任である。最終的な仕様書の修正も、人間自身が行った。AIは仕様を決定しない。Decision Automationではなく、Decision Preparationを委任した。

実際の流れは次のとおりである。現在のコードと関連情報も調査の根拠として参照した。

```text
Word仕様書
  ↓ Markdown化
分割された仕様書
  ↓ Pythonで1ファイルへ統合・再構成
GitHub Copilotによる横断レビュー
  ↓ 問題候補・関連根拠・修正候補を提示
人間が内容と変更前後を確認し、仕様として妥当か判断
  ↓ 採用した変更を人間自身が修正
仕様書へ反映
```

Copilotの確認結果をそのまま採用せず、人間が確認・判断・修正まで担当した。調査を支援する工程と、仕様を決めて変更する工程を分けた。

## Before / Afterを人間が確認する

AIの出力をそのまま仕様書へ反映することはしなかった。Beforeは現在の仕様記述、Afterは修正候補として、人間が両者と根拠を比較した。

確認したのは、意味が変わっていないか、現在の実装と整合するか、他仕様との矛盾がないか、互換性条件を壊さないか、コードだけでは把握できない事情がないかである。正しそうに見える変更も、この確認を経て採否を決めた。

古い記述や実装と一致しない記述でも、誤りに見えることと、削除・変更してよいことは別だった。過去仕様、製品条件、将来仕様との関係が分からない場合は、差異だけで変更を確定できない。

修正候補の提示からファイル更新まで自動化することは技術的には可能だった。しかし今回は、記述を変える意味、他仕様との整合、互換性、コード外の事情、誤変更の影響を確認する必要があり、自動反映を採用しなかった。AIには案を提示させ、人間が根拠と変更前後を確認して、採用した内容を仕様書へ反映した。

Change Proposal → Human Change Validation → Specification Decisionという責任工程であり、人間のレビューは最後の形式的な確認ではない。[AI出力の責任境界とHITL](/evaluation-hitl/responsibility-and-hitl/)を、仕様変更の採否判断として具体化した工程である。

## 実際に見つかったもの

レビューで確認した問題は約40件だった。すべてが修正対象だったわけではない。AIが提示した問題候補を人間が確認し、修正するものと現状維持するものを判断した。

具体例として、ある仕様書で特定コマンドの説明内容に誤りが見つかった。AIが関連仕様と現在の実装を横断調査し、記述と実装の差異を問題候補として提示した。

人間が該当仕様、関連仕様、現在の実装、修正前の記述、修正後候補を確認し、仕様書側の記述誤りと判断して、自ら修正した。コードとの差異をそのまま仕様誤りと決めたのではなく、複数の根拠から説明内容の誤りを確認した事例である。コマンド名、Syntax、内部実装は示さない。

## AIの提案を採用しなかったもの

AIが削除・修正候補として示し、コードだけを見ると変更した方がよく見える記述でも、人間が確認した結果、コード外の事情、互換性、製品条件、保守上の理由から現状維持を選んだ箇所があった。

仕様書間で条件が食い違う場合も、一方の文書や現在のコードだけを正として、もう一方を消すことはできない。適用される条件や記述の経緯を確認する必要がある。変更しない判断と、判断材料が足りず変更を確定できない状態を区別した。

不整合の発見と変更の必要性は同じではない。差異があることを調査の起点とし、その差異を残す理由があるかを確認した。AIはChange Candidateを提示し、Change Decisionは人間が行った。

## 確認できた結果と限界

68ファイル、元仕様書約30,000ページを対象としたレビューで約40件の問題を確認し、実際の仕様誤りも発見した。関連仕様と実装を判断材料として提示し、人間が修正と現状維持を選ぶレビューを行った。

今回の対象では、AIによる横断調査、人間による確認・判断・修正を組み合わせ、一連のレビューと修正を約3時間で完了した。これは今回の実績値であり、AI単体の処理時間や従来方式との比較結果ではない。WordからMarkdownへの移行やPythonスクリプトの作成を含む全工程の所要時間を示すものではない。

仕様書は長期保守で参照され続ける知識であり、誤った修正が後の判断へ影響する。修正反映を自動化すれば操作を速められるとしても、今回は品質と仕様責任を優先した。自動化できることと、自動化すべき範囲は同じではない。

ただし、従来方式との工数比較は行っていないため、削減率・短縮率・ROIは未評価である。探索負荷をAIへ移したことと、どれだけ時間が減ったかは別の評価である。

- 約40件は修正件数ではなく、レビューで確認した問題数である。
- AI検出のRecall / Precisionは厳密に測定していない。見落としがないとは言えない。
- コードだけでは判断できない仕様が存在する。
- AIの指摘にはHuman Validationが必要であり、もっともらしさだけでは採用できない。
- 時間比較とAIによる工数削減率は未測定である。ROIは推測しない。

## この事例から得た設計原則

1. **MigrationをInspection Opportunityとして利用する。** 形式移行をコピーで終えず、既存KnowledgeのDebtを点検する機会として扱う。
2. **単一Sourceを絶対視しない。** DocumentationもCodeもEvidenceであり、差異があるときは履歴や運用・互換性条件も確認する。
3. **AIへDecisionではなくInvestigationを委任する。** 不確実な仕様の最終判断ではなく、候補抽出と根拠収集を任せる。
4. **モデル性能だけでなくContext Reachを設計する。** 必要なEvidenceへのアクセス範囲を設計し、調査できる条件を整える。
5. **Human Reviewを明確な責任工程にする。** Before / Afterと根拠を比較し、変更を承認する工程として位置付ける。自動反映できる場合も、仕様責任と誤変更の影響から反映方法を選び、速度より長期利用される知識の品質を優先する。
6. **AIの指摘と変更判断を分離する。** Issue Candidate ≠ Change Decisionであり、現状維持も判断結果になる。
7. **Legacy MaintenanceではDocumentationも保守する。** コードだけでなく、仕様Knowledgeの整合と有効性も保守対象に含める。

Markdownによる構造化、PythonによるKnowledge統合、Copilotによる横断レビュー、人間による確認・判断・修正を組み合わせた。AI単体で完結させるのではなく、必要な情報構造と道具、業務の流れ、人間の判断を設計した事例である。AIへ任せたのは判断の準備であり、仕様を変える責任と最終修正は人間が担った。
