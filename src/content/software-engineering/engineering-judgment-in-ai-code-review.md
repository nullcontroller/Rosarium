## コードの説明を得ることと、動作を理解すること

AIを使うと、関連コードを探し、呼び出し関係を整理し、問題になりそうな箇所を列挙する作業を支援できる。しかし、説明が整っていることだけでは、その説明が既存システムの動作原理と一致するかは判断できない。

必要なのは、設計上成立するはずの条件と、実際のコード・仕様・実行結果を照合する力である。「この順序で終了してよいのか」「この資源は誰が解放するのか」という違和感を、確認すべき条件へ変える。AIと人間の能力を固定的に比較するより、探索の結果をどの根拠で採用するかを設計したい。

この記事では、特定の障害の原因や修正結果ではなく、リソース管理を題材に、違和感から仮説・検証・判断へ進む一般的な方法を扱う。[コード保守とAIの検証可能性](/software-engineering/code-maintenance-context/)が既存成果物を根拠として使える条件を扱うのに対し、ここでは、その根拠から何を不整合として見つけるかを掘り下げる。

## AIには探索範囲と未確認点を示させる

AIは、取得・初期化・終了・解放の処理候補、呼び出し元、エラー分岐、更新差分を探す助けになる。調査を依頼するときは、結論だけでなく、参照した箇所、そこから読み取れる事実、推測、まだ調べていない範囲を分けて出力させる。

たとえば「終了処理は正しいか」だけを尋ねるより、「取得した資源ごとに所有者・終了処理・異常時の経路を対応付け、根拠がない項目を未確認として残す」と範囲を定める。出力された対応表は完成した仕様書ではなく、コードと照合する調査用の中間成果物になる。

関連コードの取得漏れ、設定や動的な呼び出しの見落とし、古い仕様の参照、所有権の誤解は起こり得る。AIが挙げなかった経路も含め、調査対象の境界を確認する。AIの断言の強さを、根拠の強さに置き換えてはいけない。

## リソースを生成から解放まで追う

メモリ使用量の増加を調べる場合も、最初から解放漏れと決めない。キャッシュ、処理中のデータ、参照の保持、計測時点の違いなどを区別し、どの資源が、どの条件で残っているのかを確認する。

資源ごとに、次の対応を作ると調査の抜けを見つけやすい。取得と初期化、終了と解放は、APIによって一体の場合も別の場合もある。

| 観点 | 確認する条件 | 根拠の候補 |
|---|---|---|
| 取得・初期化 | どの状態まで進めば利用可能か。途中失敗時に何が残るか | API契約、戻り値、例外経路 |
| 所有権 | 誰が資源を保持し、誰が解放するか。借りた参照を解放していないか | 所有権の仕様、生成箇所、引数の契約 |
| 利用 | 利用中に必要な依存資源が有効か | 呼び出し関係、寿命、並行処理の条件 |
| 終了 | 新しい処理を止め、実行中の処理を終えられるか | 停止手順、完了通知、同期条件 |
| 解放 | 正常終了・途中失敗のどちらでも、責任者が必要な後始末を行うか | 解放経路、状態遷移、検証結果 |
| 終了後 | 再利用・再初期化・繰り返しの終了が許されるか | 公開仕様と終了後の状態 |

解放責任を寿命と結び付ける仕組みも利用できる。たとえばC++の[RAIIによる資源管理](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#Rr-raii)や、.NETの[Disposeの実装指針](https://learn.microsoft.com/en-us/dotnet/standard/garbage-collection/implementing-dispose)は、資源と責任を対応付ける具体的な手掛かりになる。ただし、借用した資源の所有権や外部サービスの停止順序まで、仕組みだけで決まるわけではない。利用するAPIの契約を確認する必要がある。

## 終了順序を見るのは、依存関係が残るため

初期化と終了を、単なる関数の対として見るだけでは不十分である。ある資源の終了処理が別の資源を使うなら、その依存先は終了処理が完了するまで有効でなければならない。

次は説明用の架空例であり、実際の製品や障害のコードを表すものではない。作業処理が、終了時の残処理を書き込むために保存先を使うという契約を仮定する。

```text
開始時：保存先を開く → 作業処理を開始する
終了時：新規受付を止める → 実行中の作業を待つ
        → 作業処理の残処理を保存する → 保存先を閉じる
```

この契約なら、保存先を先に閉じる経路は調査対象になる。違和感は「逆順でなければ何でも誤り」という直感ではなく、「残処理が保存先を使う間、その保存先が有効である」という期待と、コードの順序との差から生まれる。

終了は依存関係に応じて逆順になる場合があるが、すべてのシステムで初期化の完全な逆順にすればよいわけではない。共有資源、非同期処理、停止の待ち合わせがあるなら、所有権と実行完了の条件も追う。順序の不整合を見つけても、それが直ちにメモリリークの原因だとは断定できない。

| 問題 | 区別すべき状態 | 確かめること |
|---|---|---|
| 解放漏れ | 解放すべき資源の後始末が抜ける | 所有者と、抜けた正常・異常経路 |
| 参照保持 | 不要になった対象への参照が残る | 保持元と、本来の寿命。意図したキャッシュとの違い |
| 解放後利用 | 寿命を終えた資源へアクセスする | 呼び出しの時系列、残存参照、並行処理 |
| 二重解放 | 同じ資源を複数回解放する | 所有者の重複、解放済み状態、APIの再呼び出し契約 |
| 状態管理の不整合 | 多重初期化や終了後の再利用など、許されない遷移が起きる | 状態遷移とAPI契約。繰り返し可能な終了処理とは区別する |

観測している現象と、候補となる不具合の種類を対応付ける。説明しやすい原因へ飛び付かず、反証できる形で候補を残すことが重要になる。

## ライブラリ更新では、呼び出し側の前提も確認する

API名や引数が変わらなくても、それだけで既存コードとの整合性を保証できるわけではない。更新差分を調べる場合は、利用する版の公開API契約、変更履歴、移行ガイドを根拠にする。特定の内部実装が変わったという推測と、公開仕様で確認できた変更を混ぜない。

- 初期化と終了が対応しているか。途中失敗時に終了が必要か、不要か。
- 所有権、呼び出し可能な状態、依存関係、実行順序の制約が変わっていないか。
- 例外やエラー後にどの資源が有効か。再試行や再初期化を許すか。
- 既存コードが依存していた挙動は公開契約か、観測しただけの挙動か。

仕様差を確認できなければ「更新が原因」と確定しない。同じ入力・設定・負荷条件での比較や、対象を限定した検証によって、候補を絞る。比較できない条件と、まだ調べていない事項も残す。

## 違和感を検証可能な仮説に変える

調査記録は、「怪しい箇所」の一覧より、期待・観測・仮説・検証・判断を結ぶ形にする。架空例なら、「終了時の保存が必要」という契約に対して、「保存先が先に閉じる経路がある」という観測から、「その経路では残処理が失敗するのではないか」という仮説を立てられる。この段階では、失敗の発生も、その結果の種類も未確定である。

1. **現象と確認済み条件を固定する。** 発生条件、観測した値、未確認の条件を分ける。メモリの増加だけでリークと判定しない。
2. **AIで関連処理を探索する。** 根拠となるコードと取得範囲を添え、初期化・利用・終了・異常経路を候補として集める。
3. **設計上の期待を記述する。** 所有者、寿命、依存先、終了後の状態を、公開仕様とコードに照らして整理する。
4. **不整合の仮説を作る。** どの経路で、どの前提が崩れ、何が観測されるはずかを明示する。別の説明も残す。
5. **根拠を突き合わせる。** コード、版ごとの仕様、ログ、テスト、必要に応じた資源の計測を比較する。AIの説明だけで因果関係を確定しない。
6. **採用・修正・棄却を記録する。** 観測が予測と合わなければ仮説を見直す。再現しないことだけを、原因候補の完全な否定とはしない。
7. **変更と回帰条件を決める。** 修正が必要なら、正常終了、途中失敗、再試行、繰り返し、並行処理などから、契約に関係する経路を選んで検証する。

これは一般的な調査手順であり、すべてを実施済みとする事例報告ではない。検証環境や根拠が足りない場合は、結論の範囲を限定し、追加の調査と変更の採否を分ける。

## AIの出力を採用する条件を持つ

AIが探索し、人間が読むという分担だけでは、検証の仕組みにならない。静的解析、テスト、実行ログなどの観測手段と、仕様から導いた期待を照合する必要がある。人間も思い込みを持つため、経験者の直感だけで採否を決めない。

変更の受入条件には、今回の現象が確認できることに加え、保持すべき互換性、異常時の状態、影響範囲、未確認のリスクを含める。テストを通過しても、そのテストが扱っていない寿命や呼び出し経路まで証明したことにはならない。工程への組込みは[AIを開発工程に組み込む設計](/software-engineering/development-workflow/)、変更の採否は[コードの評価と受入条件](/evaluation-hitl/code-evaluation-acceptance/)へ接続する。

## 学ぶ対象を、判断に必要な条件へ結び付ける

AIの探索能力が進歩しても、出力を採用する条件がなくてよいことにはならない。メモリとリソース管理、所有権、ライフサイクル、API契約、依存関係、異常系、テスト、保守の知識は、何を調べれば判断できるかを定めるために役立つ。

継続学習では、用語を覚えるだけでなく、「この原則が崩れると、どの状態になるか」「それを何で観測するか」を説明できることを目指す。AIには候補探索や反例の検討を支援させ、その内容も根拠へ戻して確かめる。

技術力を「AIにできない作業」の一覧に固定する必要はない。違和感を設計上の期待として言語化し、検証できる仮説へ変え、根拠に応じて判断を更新できることが、AIを使う開発工程の信頼性を支える。
