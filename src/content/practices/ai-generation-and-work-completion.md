AIで文章を速く作れたとき、仕事も速く進んだと感じやすくなります。しかし、成果物を生成する速度と、仕事が完了するまでの時間は別です。

私自身、要件をAIで文章化した後、レビューで十分に説明できず、手戻りを起こしました。ここでは、その経験から、生成後の理解・確認・合意形成まで含めて業務を設計する必要性を考えます。

## AIで要件をMarkdownへ整理した

要件定義した内容をAIに整理してもらい、Markdown形式の成果物としてまとめ、社内の設計レビューへ持ち込んだことがありました。文章化自体は速く進み、当時は「要件を整理する → AIでMarkdown化する → 完成」と考えていました。

しかし、その形式ではレビュー側が内容を理解しにくく、私自身も設計意図や論点を十分に説明できませんでした。有効な合意形成につながらず、やり直しが発生しました。

不足していたのは、AIが整理した内容を自分で理解する工程と、相手がレビューできる成果物へ整える工程です。読み手に理解を求めるだけでなく、判断しやすい形へ変換する責任が作成側にもありました。

これはAIを使わなければ防げた、と断定できる経験ではありません。問題は、生成された文章を、そのまま業務上の完成品として扱ったことにありました。

## 中間成果物と、レビューする成果物を分ける

Markdownは、AIとの情報交換や要件の構造化、中間成果物として有用です。形式そのものを否定する必要はありません。ただし、次の三つは一致するとは限りません。

- AIが扱いやすい形式
- 自分が内容を理解しやすい形式
- 他人がレビューして判断しやすい形式

例えば、文章で列挙した要件が正しくても、既存システムとの関係や変更前後の差分を追いにくければ、レビューには追加の説明が必要です。次工程で必要なのは全文を読むことなのか、構造を確認することなのか、選択肢を比較することなのかを考えます。

**成果物の品質にはReviewabilityも含まれます。** 内容があるだけでなく、確認対象、判断の根拠、確定事項と未確定事項が分かり、次工程の人が理解・レビュー・判断できることが必要です。用途に応じて、AI向けの中間表現と人間向けの最終成果物を分けます。

## 生成時間だけでは導入効果を測れない

AI導入後の総工数を見るため、工程を次のように分解します。これは測定結果ではなく、見落としを避けるための整理です。

```text
AI導入後の総工数
= AI処理 + Human Verification + 修正 + 形式変換
  + 説明 + 手戻り + 合意形成 + 必要に応じてRecovery
```

Human Verificationには内容確認やレビューを含み、同じ作業を二重に数えません。例外対応や復旧も、発生する業務では対象に含めます。工程別の作業量としての総工数と、待ち時間や並行工程を含む業務完了までの経過時間は区別して評価します。

次は**説明用の仮例であり、今回の経験の実測値ではありません**。同じ完成条件の仕事を従来方式では60分で終えられたとして、AI導入後に以下の工程時間が順に掛かる場合を考えます。

| 工程 | 仮の時間 |
|---|---:|
| AI生成 | 10分 |
| 内容確認 | 20分 |
| 修正 | 20分 |
| 説明準備 | 20分 |
| 差し戻し対応 | 30分 |
| 工程時間の合計 | 100分 |

生成が10分でも、仕事の完了には100分掛かるという例です。AI生成の時間だけを従来の仕事全体と比べると、後工程の増加が見えません。この数字から実際の削減率やROIを主張することはできません。

評価では、同じ品質・完成条件で、開始から成果物の利用や合意までを比較します。短くなった工程と増えた工程を分け、品質、差し戻し、例外、レビュー待ちも確認します。AI OptimizationがWorkflow Optimizationにつながるかは、この範囲で判断する必要があります。

## Human Reviewにもコストがある

人間の確認は品質と安全性のために必要ですが、無料の工程ではありません。大量のAI出力をすべて最初から精査するなら、最初から人間が作業した方が速い場合もあります。

だからといって、必要な承認を省くことが解決にはなりません。生成範囲を小さくする、根拠と差分を渡す、確認しやすい形式にするなど、確認に必要な仕事を減らす余地を考えます。

誰が承認し、どの条件でAIを止め、人へ判断を戻すかは、[第1章　AIに仕事を任せても、責任は消えない](/foundations/ai-business-design/delegation-and-responsibility/)が扱う責任設計です。本稿で確かめたいのは、その責任工程を含めても、業務全体が改善しているかです。

## 図表化を、説明と理解確認に使う

この失敗以降、文章だけで終わらせず、必要に応じてシステム構成図、処理フロー、Before / After、比較表、入出力関係、責任分界へ変換するようになりました。

図表化の目的は、他者への説明と自分自身の理解確認の二つです。関係、差分、処理順序を表現すると、どこが曖昧か、何を説明できないかにも気付けます。VisualizationをCommunication AidとSelf Validationとして扱います。

ただし、図を増やせば完成するわけでもありません。比較が必要なら表、流れを確認するならフロー、と次工程の判断に合う表現を選びます。

## 自分の言葉で説明できるか

現在は、レビューへ進む前に、自分の言葉で次の点を説明できるかを確認しています。

- なぜこの要件が必要か
- なぜこの構造なのか
- 既存仕様へどう影響するか
- 何が未確定か
- どこにリスクがあるか

AIが理解したように見える文章を生成することと、自分が理解していることは別です。説明できない部分は、根拠を確認し、必要なら関係者へ問いを戻します。説明の言い回しを整えるだけで、内容の理解を代替しません。

## AIを含む業務プロセスを設計する

失敗後は、生成を完了条件にせず、次の流れで考えるようになりました。

1. 要件を整理する
2. AIで構造化する
3. 自分で内容を確認し、理解する
4. 必要に応じて図表化し、他人がレビューできる形へ変換する
5. 自分の言葉で説明できるか確認する
6. レビュー・審議で論点を確認し、合意する

AI導入を、一工程へツールを追加するだけと捉えると、生成の後にある仕事を見落とします。中間成果物、受け渡し、理解、確認、合意まで含めてProcess Redesignとして扱うことが必要です。再設計しても必ず効率化するとは限らないため、導入後の結果も評価します。

## では、何をAIへ任せるべきか

この経験から得た原則は、生成速度を成果に置き換えず、レビュー可能性と人間の理解を完成条件へ含めることです。AI出力を中間成果物として扱うかは用途によって判断し、業務の開始から完了までを評価します。

その上で、AIへ任せた後の検証・修正・復旧を含めても価値があるかを考えます。具体的な委任範囲の決め方は[AI適用可否と委任レベルの設計](/foundations/applicability-and-delegation/)で整理しています。
