## 何をする人か

ソフトウェア開発・保守を土台に、業務要求をシステム要件へ具体化し、AI・人間・既存システムをつなぐ仕組みを設計するエンジニアです。

- **Windows向け業務ユーティリティを長期間担当しています。** C# / .NETを中心に、複合機・プリンタ関連の10を超えるユーティリティについて、要件整理、設計、実装、評価、保守、変更影響分析まで経験してきました。
- **C#を主軸に、Pythonも使います。** 製品ソフトウェアではC#、文書・データ処理、調査、検証、自動化ではPythonを利用します。
- **既存システムを理解して変更します。** コード、UI、資料、実動作を突き合わせて仕様を復元し、保守、モダナイゼーション、継続・終了判断へつなげます。
- **Applied AIを業務へ組み込みます。** RAG / QA、ベクトル検索、Knowledge / Context、AI Evaluation、HITLを、業務プロセスと既存システムの中で設計します。
- **要求からアーキテクチャへつなぎます。** 与えられた業務要求を、システム要件、人とシステムの役割分担、機能・非機能要件、実現方式へ具体化します。
- **AIを使った開発そのものも設計対象にします。** 調査、仕様検討、実装、レビューをAIへ委任するときも、入力するContext、確認条件、最終判断の位置を定めます。

個別技術を並べることより、**要求 → システム要件 → アーキテクチャ → 実装・検証 → 運用・改善**をつなげられることを現在の専門性としています。

## 経験の流れ

キャリアの土台は、Windows向け業務ユーティリティの開発・保守です。長期間同じ製品群に関わる中で、既存仕様との互換性、外部システム連携、異常系、変更後の保守まで含めて考える習慣を身につけました。

その後、複数チームが関わる製品開発のプロジェクト推進を経験し、個別機能だけでなく、製品全体への影響、品質問題、優先順位、関係者間の合意を扱うようになりました。

Applied AIでは、RAG / QAの構築から始め、Knowledge、検索制御、追加確認、AIと人間の責任分界、PoC評価、運用改善まで対象を広げています。現在は、既存システムの理解・保守とAI活用を別々に扱わず、一つのシステムとして設計することを重視しています。

## 代表実績・設計事例

担当範囲と確認できる結果を分けて、実務と設計判断を公開しています。

:::case{title="仕様書を現在の実装と照合する"}
**課題：** 分割された仕様書の古い説明・誤り・矛盾を横断確認する必要がありました。

**判断・実務：** MarkdownをPythonで統合し、Copilotで現在のコードと照合。コードだけでは決まらない部分は人が判断し、最終修正も人が行いました。

**確認できる結果：** 約30,000文字・68ページの仕様書で約40件の問題を確認。AIによる調査と人の確認・判断・修正を合わせ、レビューと修正を約3時間で完了しました。

[仕様書横断レビューの実務を見る](/cases/specification-debt-review/)
:::

:::case{title="暗号処理・異常系の保守を進める"}
**課題：** 暗号方式の変更に伴い、保存情報の欠落・破損や読出し失敗への対応が必要でした。

**判断・実務：** 安全側へ止める条件、復旧方法、OS側との責務を整理。コードと背景資料を参照できるAIを使い分け、人が前提を確認して仕様・実装へつなぎました。

**確認できる結果：** 承認した仕様に基づく修正と単体テストを実施。正常系への変更を限定しました。

:::case{title="既存システムを理解・変更判断できる状態へ整える"}

**判断・実務：** コード・UI・実動作を突き合わせ、仕様と処理関係を復元。人向けの図と、RAG / QAで参照するKnowledgeへ整理しました。

**確認できる結果：** 調査結果を、後続の仕様確認・問い合わせ対応・変更判断に再利用できる形で残しました。

## 今後の方向性

現在の中心は、**要件定義・システムアーキテクチャ・Applied AI・ソフトウェア開発 / 保守**です。与えられた業務要求を、情報システムとして成立する要件と方式へ具体化するところに強みがあります。

今後は、その前段へ責任範囲を広げたいと考えています。将来的には、ITストラテジスト（ST）的な立場で、次のような判断を担うことを目指しています。

- 何を変える価値があるか
- どの業務課題・経営課題を優先するか
- 業務要件・業務目標・KPIをどう置くか
- 何をシステム化し、何を対象外にするか
- どこへ投資し、何を優先するか
- 新しく作るか、維持するか、統合するか、終了するか

つまり、**「どう作るか」だけでなく、「何を、なぜ、どこまで実現するか」から関わる技術者**へ専門領域を広げたいと考えています。企画と要件定義・システムアーキテクチャの境界は[企画](/planning/#handoff)で整理しています。

## 志向する働き方

自社側の技術専門職（IC）として、一つのシステムやサービスへ長期的に関わり、企画・業務要件からシステム要件、アーキテクチャ、実装・検証、本番運用、改善までをつなぐ仕事を志向しています。

一方、**FDE、顧客常駐・顧客折衝を中心とする役割、短期PoCを顧客ごとに反復することが中心の役割は、現在の志向対象ではありません。** 職種そのものの優劣ではなく、長期Ownershipを持って仕組み全体を育てたいというキャリア志向との違いです。
