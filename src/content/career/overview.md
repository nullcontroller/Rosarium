## 何をする人か

ソフトウェア開発・保守を土台に、要求をシステム要件へ具体化し、AI・人間・既存システムをつなぐ設計を行うエンジニアです。

- **Windows向け業務ユーティリティを長く担当する。** C# / .NETを中心に、複数の業務ユーティリティについて、要件整理、設計、実装、評価、保守、変更影響分析まで継続して担当しています。
- **C#を主軸に、Pythonも使う。** 製品ソフトウェアではC#、文書・データ処理、調査や検証の自動化ではPythonを利用します。
- **既存システムを理解して、安全に変える。** コード、UI、既存資料、実動作を突き合わせて仕様を整理し、保守・モダナイゼーション・終了判断へつなげます。
- **Applied AIを業務へ組み込む。** RAG / QA、Knowledge / Context、AI Evaluation、HITLを、単体技術ではなく業務と既存システムの中で設計します。
- **要求からアーキテクチャへつなぐ。** 与えられた業務要求を、システム要件、人とシステムの役割分担、機能・非機能要件、実現方式へ具体化します。
- **将来はシステム企画・ストラテジ領域へ広げる。** 「何を、なぜ、どこまで実現するか」を判断する、ITストラテジスト（ST）的な価値発見・業務要件・投資・優先順位の領域を深めたいと考えています。

## 現在の専門性

| 専門性 | できること |
| --- | --- |
| Applied AI / RAG / QA | 回答に必要な知識、検索条件、不足情報の確認、有人対応への引継ぎを組み合わせる。 |
| 評価・HITL | 根拠の適合性、回答品質、停止条件と人が判断する場面を分けて設計する。 |
| コンテキスト・ナレッジ設計 | コード・資料・実動作の情報を整理し、人とAIが参照・検証できる形へ整える。 |
| 要件定義・システム設計 | 与えられた業務要求を、機能・非機能要件、責任分担、実現方式へ具体化する。 |
| ソフトウェア開発・既存システム保守 | C# / .NETを中心にWindows向け業務ユーティリティを長期担当。Pythonも調査・データ処理・検証に利用し、変更影響と異常系を確認して実装・評価・保守へつなぐ。 |

AIを使った開発・保守でも、調査、仕様検討、実装、レビューの受け渡しに必要な情報と確認条件を設計します。

## 価値をどう作るか

現在は、与えられた課題と要求を整理し、システム要件 → アーキテクチャ → 実装・検証 → 運用・改善へつなぐことに強みがあります。設計案・評価条件と、実装して確認できた結果を分けて示します。

今後は、現在の要件定義・アーキテクチャ・Applied AIの経験を土台に、その前段の価値発見 → 業務課題の選定 → 業務要件・業務目標 → システム化範囲へ射程を広げたいと考えています。検証や利用結果から前段へ戻る反復も含めて、継続的に価値を育てる仕事を志向しています。

## 代表実績・設計事例

実際に行った作業と、設計能力を示す事例を4件紹介します。担当範囲と結果の根拠は、各実践事例で確認できます。

:::case{title="仕様書を現在の実装と照合する"}
**課題：** 分割された仕様書の古い説明・誤り・矛盾を横断確認する必要がありました。

**判断・実務：** MarkdownをPythonで統合し、Copilotで現在のコードと照合。コードだけでは決まらない部分は人が判断し、最終修正も人が行いました。

**確認できる結果：** 約30,000文字・68ページの仕様書で約40件の問題を確認。AIによる調査と人の確認・判断・修正を合わせ、レビューと修正を約3時間で完了しました。

[仕様書横断レビューの実務を見る](/cases/specification-debt-review/)
:::

:::case{title="暗号処理・異常系の保守を進める"}
**課題：** 暗号方式の変更に伴い、保存情報の欠落・破損や読出し失敗への対応が必要でした。

**判断・実務：** 安全側へ止める条件、復旧方法、OS側との責務を整理。コードと背景資料を参照できるAIを使い分け、人が前提を確認して仕様・実装へつなぎました。

**確認できる結果：** 承認した仕様に基づく修正と単体テストを実施。正常系への変更を限定しました。

[レガシー保守の判断と実装を見る](/cases/three-ai-maintenance/)
:::

:::case{title="既存システムを理解・変更判断できる状態へ整える"}
**課題：** 内部仕様が共有されず、問い合わせのたびに調査が必要でした。

**判断・実務：** コード・UI・実動作を突き合わせ、仕様と処理関係を復元。人向けの図と、RAG / QAで参照する知識へ整理しました。

**確認できる結果：** 調査結果を、後続の仕様確認・問い合わせ対応・変更判断に再利用できる形で残しました。当時のAI環境で行った仕様復元・ナレッジ再構築の参考事例です。

[システム理解とナレッジ再構築を見る](/cases/system-understanding/)
:::

:::case{title="顧客サポートの業務要求をシステム要件へ落とす"}
**課題：** 企画側から与えられた工数削減・顧客の自己解決という業務目標を、実現可能な要件へ具体化することです。

**判断・設計：** 不足情報の追加確認、回答根拠、有人引継ぎを要件化し、生成AI・ベクトル検索・RAG・HITL、ナレッジ運用、PoCの評価条件を設計しています。

**確認できる内容：** 与えられた業務要求をシステム要件へ具体化し、回答品質と有人対応への引継ぎを支える方式・ナレッジ・PoCの評価条件を設計する判断を確認できます。

[顧客サポートQAの要件・方式設計を見る](/cases/customer-support-ai-dx/)
:::

## 仕事で重視すること

- **課題から始める。** 誰のどんな困りごとを減らすかを確認し、既存の仕組みや業務手順で解決する選択、AIを使わない選択も比較します。
- **役割と根拠を明確にする。** AIへ渡す情報、検証条件、人が判断・承認する位置と責任を設計します。
- **維持と終了まで考える。** 作って終わりにせず、利用結果から見直し、必要なら変更・統合・終了を判断します。

判断原則の詳細は[AI設計](/ai-design/)と[DX](/dx/)に整理しています。

## 経験と現在の仕事のつながり

ソフトウェア開発・保守では、既存資産と制約を前提に変更する力を培ってきました。要件分析では曖昧な要求を具体化し、プロジェクト推進では全体への影響と関係者の調整を考える経験を重ねました。

**問い合わせ起点の課題具体化。** 問い合わせを起点に利用者の状況や課題を整理し、必要な情報を集め、技術的な問題を調査・判断できる形へ具体化する実務を経験しました。仕様・コード・実動作の確認を通じて、利用側の問いを要件分析・技術調査・システム理解へつなげています。

生成AI / RAGへの取り組みは、その経験を、知識・検索・人による判断・評価を含む業務システムの設計へつないでいます。AIの導入そのものより、実務で確認・利用できる仕組みにすることを重視しています。

## 今後深めたい領域

与えられた課題をどう実現するかに加え、そもそも何を変える価値があるのかを見つけ、業務要件を定義するところから関わりたいと考えています。システム企画、価値発見、業務要求の定義を、今後深めたい専門領域として位置付けています。

価値・業務課題の発見、現状とあるべき姿、KPI・業務成果、システム化する範囲と対象外、投資・優先順位、AIや新技術を採用するか、既存システムを刷新・維持・縮小・廃止するかを扱いたいと考えています。その判断を業務要件へまとめ、システム要件の定義へ渡す考え方は[企画](/planning/#purpose)で整理しています。

## 今後取り組みたい仕事

以前から、顧客や利用者の要望を受けて個別に対応する仕事よりも、何を変える価値があるのかを考え、仕組み全体を設計・改善する仕事に強く関心がありました。

その後、問い合わせ起点のFDE型実務を経験し、一つのシステムやサービスを長期的に育てる仕事に強く関心があるという、以前からの自己認識を再確認しました。

現在の要件定義・アーキテクチャ・Applied AIの経験を土台に、今後は価値発見、業務要求、システム企画へ関与を広げたいと考えています。将来的には、ITストラテジスト（ST）的な「何を、なぜ、どこまで実現するか」という判断から、システム要件、設計、実装・検証、本番運用、改善までをつなげられる技術専門職を志向しています。

FDE、顧客常駐・顧客折衝を中心とする役割は、現在の志向対象ではありません。顧客ごとの短期案件を反復するより、自社側で一つの仕組みの責任を長期的に持ち、価値発見・システム企画・業務要求から運用・改善まで継続して関わる仕事を志向しています。
