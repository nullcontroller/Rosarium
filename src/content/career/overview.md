## 何をする人か

立林裕太朗です。ソフトウェア開発・保守、要件分析、プロジェクト推進の経験を基に、生成AI / RAGを業務と既存システムへ組み込む設計に取り組んでいます。要求をシステム要件へ具体化し、AI・人間・既存システムの役割、検証と運用の条件をつなぐことが現在の軸です。

## 現在の専門性

| 専門性 | できること |
| --- | --- |
| Applied AI / RAG / QA | 回答に必要な知識、検索条件、不足情報の確認、有人対応への引継ぎを組み合わせる。 |
| 評価・HITL | 根拠の適合性、回答品質、停止条件と人が判断する場面を分けて設計する。 |
| コンテキスト・Knowledge設計 | コード・資料・実動作の情報を整理し、人とAIが参照・検証できる形へ整える。 |
| 要件定義・システム設計 | 与えられた業務要求を、機能・非機能要件、責任分担、実現方式へ具体化する。 |
| ソフトウェア開発・既存システム保守 | 変更影響と異常系を確認し、承認した仕様に基づく実装・単体テストへつなぐ。 |

AIを使った開発・保守でも、調査、仕様検討、実装、レビューの受け渡しに必要な情報と確認条件を設計します。

## 価値をどう作るか

現在は、与えられた課題と要求を整理し、システム要件 → アーキテクチャ → 実装・検証 → 運用・改善へつなぐことに強みがあります。設計案・評価条件と、実装して確認できた結果を分けて示します。

今後は、その前段の価値発見 → 業務課題の選定 → 業務要件・業務目標 → システム化範囲まで関わりたいと考えています。この全体を既に一貫して担当したという意味ではありません。検証や利用結果から前段へ戻る反復も含めて、仕事の射程を広げたいと思っています。

## 代表実績・設計事例

実際に行った作業と、設計能力を示す事例を4件紹介します。担当範囲と結果の根拠は、各Caseで確認できます。

:::case{title="仕様書を現在の実装と照合する"}
**課題：** 分割された仕様書の古い説明・誤り・矛盾を横断確認する必要がありました。

**判断・実務：** MarkdownをPythonで統合し、Copilotで現在のコードと照合。コードだけでは決まらない部分は人が判断し、最終修正も人が行いました。

**確認できる結果：** 約30,000文字・68ページの仕様書で約40件の問題を確認。AIによる調査と人の確認・判断・修正を合わせ、レビューと修正を約3時間で完了しました。

[仕様書横断レビューの実務を見る](/cases/specification-debt-review/)
:::

:::case{title="暗号処理・異常系の保守を進める"}
**課題：** 暗号方式の変更に伴い、保存情報の欠落・破損や読出し失敗への対応が必要でした。

**判断・実務：** 安全側へ止める条件、復旧方法、OS側との責務を整理。コードと背景資料を参照できるAIを使い分け、人が前提を確認して仕様・実装へつなぎました。

**確認できる結果：** 承認した仕様に基づく修正と単体テストを実施。正常系への変更を限定しました。

[レガシー保守の判断と実装を見る](/cases/three-ai-maintenance/)
:::

:::case{title="既存システムを理解・変更判断できる状態へ整える"}
**課題：** 内部仕様が共有されず、問い合わせのたびに調査が必要でした。

**判断・実務：** コード・UI・実動作を突き合わせ、仕様と処理関係を復元。人向けの図と、RAG / QAで参照する知識へ整理しました。

**確認できる結果：** 調査結果を、後続の仕様確認・問い合わせ対応・変更判断に再利用できる形で残しました。当時のAI環境による参考事例で、現在の推奨手順や全面刷新の完了を示すものではありません。

[システム理解とKnowledge再構築を見る](/cases/system-understanding/)
:::

:::case{title="顧客サポートの業務要求をシステム要件へ落とす"}
**課題：** 企画側から与えられた工数削減・顧客の自己解決という業務目標を、実現可能な要件へ具体化することです。

**判断・設計：** 不足情報の追加確認、回答根拠、有人引継ぎを要件化し、生成AI・ベクトル検索・RAG・HITL、Knowledge運用、PoCの評価条件を設計しています。

**確認できる内容：** 要件・方式・品質評価の判断を示します。業務目標を自ら企画した事例ではなく、目標値や効果試算も実測した導入成果としては扱いません。

[顧客サポートQAの要件・方式設計を見る](/cases/customer-support-ai-dx/)
:::

## 仕事で重視すること

- **課題から始める。** 誰のどんな困りごとを減らすかを確認し、既存の仕組みや業務手順で解決する選択、AIを使わない選択も比較します。
- **役割と根拠を明確にする。** AIへ渡す情報、検証条件、人が判断・承認する位置と責任を設計します。
- **維持と終了まで考える。** 作って終わりにせず、利用結果から見直し、必要なら変更・統合・終了を判断します。

判断原則の詳細は[AI設計](/ai-design/)と[DX](/dx/)に整理しています。

## 経験と現在の仕事のつながり

ソフトウェア開発・保守では、既存資産と制約を前提に変更する力を培ってきました。要件分析では曖昧な要求を具体化し、プロジェクト推進では全体への影響と関係者の調整を考える経験を重ねました。

生成AI / RAGへの取り組みは、その経験を、知識・検索・人による判断・評価を含む業務システムの設計へつないでいます。AIの導入そのものより、実務で確認・利用できる仕組みにすることを重視しています。

## 今後深めたい領域

与えられた課題をどう実現するかだけでなく、そもそも何を変える価値があるのかを見つけ、業務要件を定義するところから関わりたいと考えています。System Planning / Value Discovery / Business Requirementsは、今後深めたい専門領域です。現在、企画を担当した公開可能な実務Caseはありません。

価値・業務課題の発見、As-Is / To-Be、KPI・業務成果、システム化する範囲と対象外、投資・優先順位、AIや新技術を採用するか、既存システムを刷新・維持・縮小・廃止するかを扱いたいと考えています。その判断を業務要件へまとめ、システム要件の定義へ渡す考え方は[企画](/planning/#purpose)で整理しています。

## 今後取り組みたい仕事

業務要求を要件・アーキテクチャへ具体化し、AIとソフトウェア開発の両方を使って、導入後の評価・改善まで継続的に関われる仕事を志向しています。自社側で一つのサービスやシステムの責任を長期的に持ち、今後は価値発見や企画判断にも関与を広げたいと考えています。

実装だけ、短期PoCだけ、営業や組織管理だけで役割が完結する仕事は、この方向性との接点が少なくなります。職種名ではなく、扱う判断と継続的に責任を持てる範囲から相性を考えています。

FDE的な仕事も、現場での具体化に加え、価値発見・業務要件・導入後の改善まで関われるかという同じ観点で捉えます。
