## 方式の見込みから、要求に対する合否判定へ

**確定した要求・仕様を期待結果へ落とし込み、QAシステム全体が満たすべき条件を厳格に確認するテストを設計します。**  
この記事は、[顧客サポートDXの本編Book](/cases/customer-support-ai-dx/)を補完する、同じ設計事例のテスト計画です。  
専用の問い合わせ支援システムがない業務へ顧客向けQAを新規開発する前提を引き継ぎ、追加質問・検索・回答許可・回答生成・有人引継ぎを対象にします。

### PoCとテストで、判断することを分ける

| 工程 | 時期と目的 | 対象と判断 |
| --- | --- | --- |
| PoC | 本格開発前に、候補方式を試して課題を発見・改善する | 1,000件の検証シナリオで方式の成立性と採用範囲を評価する |
| システム適格性確認テスト | 開発後に、確定した要求・仕様への適合を確認する | 別途選定する500件で、期待結果と回答品質を照合して合否を判定する |

**テストの500件は、PoCの1,000件とは別の計画です。**  
PoCで得た96％を、そのままシステム適格性確認テストの合格結果へ転用しません。  
方式の試行・改善の経緯と評価値は[独立したPoC記事](/evaluation-hitl/customer-support-qa-poc/)で扱います。

## 業務上の三分類と、三つの処理経路は別の軸

業務上の分類は、何を自動回答の対象とし、どこから専門判断を必要とするかを定めます。  
処理経路による区分は、システムの主要な分岐を漏れなく確認するために使います。

| 業務上の分類 | 回答の条件 | 主に確認する処理経路 |
| --- | --- | --- |
| 定型回答可能 | 適合する根拠があり、専門判断を要さず、自動回答が許可される | 必要情報がそろえば経路1、不足情報を取得する場合は経路2 |
| 専門判断が必要 | 根拠があっても、切分けや個別判断を担当者が行う | 自動回答を止める経路3 |
| 回答根拠不足 | 既存の資料で回答を確定できず、追加調査が必要 | 推測回答を止める経路3 |

**文書を取得できることと、自動回答を許可できることは別です。**  
対象機種・環境・版数による検索対象の適格性と、回答項目の許可・適用条件・専門判断条件を、[本編の責任境界](/cases/customer-support-ai-dx/responsibility-boundary/)と同じ二段階の制御として確認します。

### 処理経路で確認すること

| 経路 | 入力の前提 | 期待する処理と結果 |
| --- | --- | --- |
| 1. 追加質問なしで自動回答 | 必要情報がそろい、適合する根拠と回答許可がある | 不要な追加質問を行わず、条件に合う文書から根拠に沿う回答を生成する |
| 2. 追加質問後に自動回答 | 情報が不足するが、顧客の回答で条件を確定できる | 必要事項を質問し、得た機種・環境・エラー等を検索と回答可否の判定へ反映する |
| 3. 自動回答せず有人引継ぎ | 専門判断、根拠不足、原因未特定、回答許可・適用条件の不成立がある | 推測で回答せず停止する。確認済み事項・調査結果・参照文書・未解決事項・停止理由を渡し、担当者が調査を続けられる |

自動回答へ進めるケースだけでなく、**回答してはいけないケースで止まり、必要情報を引き継げること**も適合性の対象です。  
担当者が調査を再開する情報の構成は[本編の有人引継ぎ](/cases/customer-support-ai-dx/human-handoff/)へ接続します。

## 500件は、発生頻度より処理経路の確認を優先する

過去の問い合わせから500件を選定し、三つの処理経路をほぼ同数含むテストケースを構成する計画です。  
各経路の正確な内訳は確定していないため、経路別の件数は置きません。

実運用の発生割合で抽出すると、発生頻度の低い経路を十分に確認できないおそれがあります。  
機種や症状の組合せを増やすだけでなく、追加質問の要否、回答許可、停止・引継ぎという主要な処理を、重複を抑えて確認することを優先します。  
この配分から算出した割合を、そのまま運用時の自己解決率へ換算しません。

## 入力・参照資料・判定条件を管理する

各ケースに識別子を付け、実行前に入力条件と期待結果を定義します。  
変更前後を比較できるよう、次の条件と実行記録を対応付けます。

| 管理対象 | 固定・記録する内容 |
| --- | --- |
| 入力データ | 初回問い合わせ、追加質問への回答、取得すべき条件、対象経路 |
| 参照資料 | 資料の版と範囲、回答根拠として取得すべき文書・適合条件 |
| 検索対象のメタデータ | 対象機種・利用環境・対応版数と、取得してよい文書の範囲 |
| 回答項目のメタデータ | 自動回答可否・適用条件・専門判断条件と、期待する許可判定 |
| モデル・指示文 | モデルの識別・版、指示文、評価時の設定 |
| 期待結果 | 追加質問の要否、確認する項目、根拠文書の条件、自動回答か有人引継ぎか、保持する情報 |
| 実行ログ | 使用した条件の組合せ、追加質問と回答、検索条件と取得文書、許可判定、停止理由、生成回答、最終経路、引継ぎ情報 |

**条件を再現できることと、生成文が毎回完全に一致することは区別します。**  
資料・モデル・指示文などを変更した場合は、その変更を記録して比較し、異なる条件の実行結果を同じ結果として扱いません。

## 一連の処理を自動実行し、期待結果と照合する

自動化は、定型的な実行・記録・照合を先に処理し、業務専門家が内容を判断すべき対象を明確にするための設計です。

1. テストデータと評価条件を読み込み、問い合わせを入力する。
2. 追加質問が発生した場合は、ケースで定義した回答を入力する。
3. 文書検索、回答許可の照合、回答生成または停止・引継ぎまで実行する。
4. 各工程の実行ログをケースの識別子と結び付ける。
5. 事前定義した期待結果と実行ログを自動照合し、不一致を一覧にする。
6. テスターが不一致を調査し、専門的な内容判定が必要な記録をCS部へ渡す。

### 自動照合する事項

| 確認項目 | 期待結果との照合 |
| --- | --- |
| 追加質問と情報取得 | 質問の要否、必要項目の取得、確認済みの値が後続処理へ渡されたか |
| 検索対象と取得文書 | 機種・環境・版数に適合し、事前定義した文書や条件を満たしたか |
| 回答許可 | 自動回答可否・適用条件・専門判断条件を正しく照合したか |
| 最終的な処理経路 | 自動回答・有人引継ぎの期待経路へ進み、停止すべきケースで回答しなかったか |
| 引継ぎ情報 | 確認済み事項、調査結果、参照文書、未確認事項、停止理由が保持されたか |

生成回答の文章全体を、期待する回答文との完全一致で採点する方式にはしません。  
質問が原因の絞込みに有効か、回答が根拠に沿い顧客へ提示できるかは、次の専門判定へ分けます。

### 不一致ケースを調査する

テスターは期待値と実際の値、取得文書、会話と判定記録を照合し、情報収集・検索対象制御・回答許可・停止・引継ぎのどこで不一致が生じたかを調べます。  
期待結果の誤りが疑われる場合も、実装側の結果へ合わせて書き換えず、要求・仕様とCS部の判断へ戻して確認します。

修正後は同じ条件で再実行し、不一致ケースだけでなく、変更の影響を受ける従来の正常な経路も確認する計画です。  
実行条件や結果を残し、修正前の不一致と再実行後の判定を追跡できるようにします。

## テスターとCS部の専門判定を分担する

| 判定主体 | 判定すること | 判断の根拠 |
| --- | --- | --- |
| テスター | 自動実行・ログ取得・照合結果の確認、不一致調査、情報保持と処理経路の確認 | 事前定義した期待結果、入力条件、実行ログ |
| 経験豊富なCS部担当者 | 追加質問が原因の絞込みに有効か、回答が根拠と整合し無修正で顧客へ提示可能か、引継ぎから専門調査を続けられるか | 顧客の問い合わせ、会話、取得文書、回答内容、調査結果 |

CS部は、必要な内容が回答へ含まれ、根拠にない条件や操作を足しておらず、顧客が実施すべき操作を理解できるかを確認します。  
表現が違っても同じ意味を伝えられるため、語句の一致だけで合否を決めません。

**全項目を専門家へ委ねず、意味と業務上の妥当性を判断する項目へ確認を集中させます。**  
自動照合で問題がなくても、それだけで顧客へ提示できる品質と判定せず、専門判定の結果も合否へ反映します。

## システム全体の合格基準と判定方法

| 要求 | 母数と判定条件 | 合格基準 |
| --- | --- | --- |
| 定型問い合わせの自動回答 | 自動回答対象として事前定義した定型ケース（経路1・2）のうち、根拠と許可条件に適合し、CS部が無修正で顧客提示可能と判定した回答の割合 | **自動回答80％以上** |
| 専門判断・根拠不足案件の有人引継ぎ | 事前定義した専門判断・根拠不足の対象ケースで、自動回答を停止し、必要情報を保持して担当者が対応を継続できる割合 | **適切な有人引継ぎ100％** |

80％の分母は500件全体ではなく、自動回答対象の定型ケースです。  
100％の分母も、専門判断・根拠不足として選定した対象ケース集合です。  
回答許可・適用条件が成立しないケースも経路3として確認し、許可されない回答を通した状態ではシステム全体を合格にしません。

テスターの照合結果とCS部の内容判定をケースごとにまとめ、要求ごとの割合と未解決の不一致を確認します。  
どちらかの基準を満たさなければ、または要求に反する停止漏れなどが残れば、修正と再確認へ戻します。  
未確認のケースを成功扱いせず、必要な判定がそろってから合否を決める設計です。

## 設計上の到達点と、本編・PoCとの接続

この計画では、**三つの処理経路、再現条件、自動実行・照合、専門判定、合格基準を一つの判定手順へ接続しました。**  
ここに示すのはテスト設計であり、500件の実施完了・合格実績や本番効果を示すものではありません。  
テスト対象での適合を確認しても、将来の全問い合わせで誤りが発生しない保証にはしません。

業務要求とシステム方式は[本編Book](/cases/customer-support-ai-dx/)、本格開発前の課題発見と方式改善は[PoC記事](/evaluation-hitl/customer-support-qa-poc/)で扱います。  
一般的な評価の考え方は[QAチャット評価設計思想](/evaluation-hitl/qa-evaluation/)へ接続します。
